## Why

issue #76：**PDCA が回っていない**。毎日 15 分の競プロと 15 分の設計をこなしてゲートを開けているだけで、途中から「なんでやっているのか」を失う。目標設定が不明確（期限がない・どんな状態になりたいかが観測されない）で、1ヶ月は長すぎて決意が続かない。

現状の目標（30日チャレンジ）には、issue が求めるものが**構造的に無い**：

| issue #76 の要求 | 現状 |
|---|---|
| 「1ヶ月で例えばどんな状態になっていたい」 | `purpose`（目的の一文）はあるが、カードに小さく出るだけで観測されない |
| 「一週間平均で2時間以上このタブグループに費やす」 | **表現できない**。ルールは日次閾値のみで、平均は `evaluateDay` の当日 AND モデルに乗らない |
| 「今のところこれくらいで、あと何時間必要なのか」 | **どこにも出ていない** |
| 「一ヶ月が長すぎる」「一週間くらいお試しをしたい」(#65) | 期間は **30日固定** |
| 「試験勉強はもう大丈夫だから切り替えたい」 | 途中で降りられない（削除は作成当日のみ・「終える」は完走後のみ） |
| 「目標の追加・消去・変更の歴史が欲しい」 | 沿革は**1つの目標の中**のルール操作のみ。目標をまたぐ年表が無い |

要求のほとんどは**既存資産の解放**で満たせる。`end_day` カラムも前方向の延長ロジックも既にあり（`goal-lifecycle-fork`）、「終える」（永続ルールをゲートから外し、レポート・沿革は残す）も既にあり、`purpose` も既にある。**本当に新しいのは「目標時間」ひとつ**である。

本変更は、目標を「**期限つき・目標時間つき・いつでも終われるもの**」にし、目標タブを開いた瞬間に現在地が読めるようにする。詳細は `ユーザーフロー.md` を**唯一の受け入れ基準**とする。

## What Changes

- **目標時間を新設**する。**1目標につき最大1つ・任意**。単位は**1日あたり**。
  - 対象は時間型のみ（**グループ／総作業時間／カテゴリ**）。**グループは複数を束ねられる**（`アルゴリズム` or `Python` の合計で2時間）。
  - **解錠ゲートへ合流してはならない**（MUST NOT）。平均は日次では確定せず `evaluateDay` の当日 AND モデルに乗らない。加えて、ゲートに乗せると目標時間が実質の下限になり二段構えが消える。
  - **目標時間を持たない目標は、ペース表示が出ないだけ**。特別扱い・例外分岐を持たない（issue #76 コメントで「全く決まっていない」とされた「ルックス改善のような目標のレポート」は、目標時間が任意である以上、決めることが無い）。
- **ペース表示**を目標カードに出す。`平均 1h24m / 2h` と **「今日 あと 3h48m で到達」**。
  `今日あと = max(0, 目標時間 × 経過日数（今日を含む） − 現在の累計)`。到達済みは数字を出さない（追い立てない）。
- **期限を作成時に自由に指定できる**ようにする。**30日固定を撤廃**する（1週間 / 2週間 / 30日は入力補助のボタンにすぎない）。issue #65「一週間の長期目標も作れるようにしたい」もこれで満たす。
  - **期限の短縮は引き続き提供しない**（MUST NOT）。`end_day` は前方向にのみ動く既存の不変条件（`goal-lifecycle-fork`）を壊さない。短くしたいときは「終えて、作り直す」。
- **めざす状態を必須にする**。既存の `purpose`（目的の一文）を任意から必須へ昇格し、カードに常時表示する。「終わるときにこれができたかを聞かれる」ことをフォーム上で明示する。
- **作成理由（「なぜ始めるのか」）を新設し、必須**にする。本アプリではルールの追加・変更・削除がすべて理由必須なので、目標そのものにも同じ扱いを与える。終えるときの理由と**対**になって大きい沿革に並ぶ。
- **証拠写真を作成時に設定できる**ようにする。「終わるときに写真を出すか」を決め、求めるなら**キャプションを1つ**決める。**初期写真（Before）は任意**（置いても置かなくてもよい）。キャプションはそのまま**レポート③の Before/After のグループ化キー**になるため、保存基盤もキャプション体系も新設しない。
- **いつでも理由つきで終えられる**ようにする。「終える」の発火を完走後限定から**進行中を含むいつでも**へ広げる。終わるとき（途中終了・完走の「終える」の**両方**）に次の3つを聞く：
  - **めざした状態の答え**（**3値・任意**：できた／できなかった／答えない）。白黒つかないことがあるため必須にしない。**本人の自己申告であってシステムは検証しない**（既存の `MANUAL_CHECK` と同じ名誉ベース）。
  - **証拠写真**（任意）。作成時に決めたキャプションで保存され、レポート③の After になる。後から出すこともできる。
  - **理由**（**必須**。従来の完走フォークでは任意だったものを昇格）。
  - **効くのは当日から**。既存の `editable-rule-registry`「ルールはいつでも追加・変更・削除でき**当日から効く**」にそろえる（目標を終えることは、その目標の永続ルールをまとめて削除することに等しい）。ゲート回避目的の終了に対する抑止は、**その事実と理由が大きい沿革に残ること**が担う。仕掛けで塞ぐのではなく逃げた事実を記録に残すという既存の思想に一致する。終えた目標のレポート・沿革・カレンダーは読めるまま残す。
- **大きい沿革（目標の年表）**を目標タブのカード一覧の下に新設する。目標の**作成・終了・完走**と、**始めた理由／終えた理由**／**目標時間の到達・未達**／**めざした状態の答え**／**証拠写真**を `day_key` 昇順で決定的に並べる。既存の⑤沿革（`goal-chronicle`＝1目標の中のルール操作と凍結の年表）とは粒度が1段違う別物。
  - 目標時間の数字だけでは「2時間やったが、で？」に終わる。**めざした状態の答えと証拠写真が並んで初めて**「時間は足りなかったが状態には届いた」「時間は足りたが状態には届かなかった」が読める。ここが大きい沿革の主役である。
  - **大きい沿革では `✓` / `×` を使ってよい**（他の画面には持ち込まない）。判定は**診断であって断罪ではなく**、`×` が一目で拾えないと「沿革を眺めて次の一手を考える」という用途自体が成立しない。ただし合格・不合格・スコア・ランク・紙吹雪は依然として出さない（MUST NOT）。
- **今日タブは1行の導線**を最上部に足す。目標時間を持つ進行中の目標について `平均 X / 目標Y` と `今日 あと Z` を出し、押すと目標タブへ飛ぶ。**既存のゲート表示・条件の進捗・パスワード動線は一切変更しない**（MUST NOT）。
- **レポート②に目標時間の破線を1本**足す。新しいブロックは足さない。

## Capabilities

### New Capabilities
- `goal-target-hours`: 目標時間の定義（1日あたり・1目標に最大1つ・任意・複数グループの束ね・作成時に固定）、ペースの算定式、到達判定（期間平均）、解錠ゲートへの非合流、目標カードと今日タブでの表示。
- `goal-history`: 大きい沿革（目標の年表）。目標の作成・終了・完走と、理由・目標時間の到達/未達・めざした状態の答え・証拠写真を決定的な順で並べ、消さないこと。

### Modified Capabilities
- `goal-challenge`: 期間の30日固定を撤廃し、作成時に期限を指定する。**めざす状態を必須**にする。目標時間と証拠写真の設定を任意で持つ。
- `goal-lifecycle-fork`: 「終える」を完走後限定から**いつでも**へ広げ、終わるときに**めざした状態の答え・証拠写真・理由**（理由のみ必須）を聞き、**当日から効く**ことを規定する。
- `goal-report`: ②時間の推移に**目標時間の水準線**を1本加える（目標時間がある場合のみ）。③には証拠写真が既存のキャプション機構でそのまま流入する（③の仕様は変更しない）。

## Impact

- **DB**: `goal_target_hours`（目標時間・1目標に高々1行）と `goal_target_hours_member`（束ねる対象の参照）を追加。`goal` へ作成理由（`start_reason`）、終了関連カラム（`ended_day_key` / `end_reason` / `final_pace_json`）、証拠写真・状態判定のカラム（`outcome_caption` / `outcome_met`）を追加。マイグレーション追加（`server/src/db/migrations.ts`）。
- **作成 API**: `POST /api/goals` が `endDay` を受け取る（30日既定を撤廃）。`purpose` と `startReason` を必須にする。`targetHours` と `outcomeCaption` を任意で受け取る。
- **証拠写真**: 保存先は既存の `goal_image`（`goal_id`＋`day_key`＋キャプション）。初期写真は既存の作成フォームのステージング機構（`goals.js` の `buildCreateImageStager`）を再利用して Day1 に保存する。**新しい保存基盤を足さない。**
- **サービス**: `server/src/services/goals.ts` に目標時間の集計とペース算定を追加。実測秒の取得は既存集計に委譲（グループは**名前＋色 identity** で束ねる `today-group-breakdown` と同じ規則）。
- **`rules/evaluate.ts` は変更しない**。目標時間はゲートに合流しないため、1行も触らない（`git diff` が空であることを最終確認に含める）。
- **終了**: 既存の「終える」処理（永続ルールを `status='removed'`）を進行中でも呼べるようにする。発効は当日のまま（既存挙動を変えない）。`goal-freeze` の凍結中・予約中との相互作用を規定する。
- **契約**: `packages/contract/src/index.ts` に `GoalTargetHours` / `GoalPace` / `GoalHistoryEntry` を追加。
- **ダッシュボード**: 目標タブ（作成フォームの期限・目標時間、カードのペースブロック、「終える」導線、大きい沿革）、今日タブ（最上部の1行）。振り返りタブ・カンバンは触らない。
- **デモモード**: `demo-seed.ts` に目標時間を持つサンプルと、終了した目標1本（理由つき）を固定 `day_key` で追加し、`demo.test.ts` の期待値を更新する。既存の達成 24/30・中盤の谷の筋書きを壊さない。
- **e2e**: 既存 Playwright に、ユーザーフローの背骨（期限を指定して作成 → カードにペースが出る → 理由つきで終える → 大きい沿革に載る）を通す1本を追加する（apply 側で DOM 確定後に書く）。
