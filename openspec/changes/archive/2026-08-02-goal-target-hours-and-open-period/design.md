## Context

`ユーザーフロー.md` が本変更の**唯一の受け入れ基準**である。この design はそれを実装に落とすための判断だけを書く。

前提となる既存の作り：

- 解錠評価（`server/src/rules/evaluate.ts`）は当日の実効条件を AND 評価し、`unlock_evaluation.per_condition_results` にスナップショットして latch する。**当日で閉じたモデル**であり、期間平均を表現する余地が無い。
- 目標は `start_day` / `end_day` を持ち、`end_day` は**前方向にのみ**動く（末尾を越えるルールと凍結の2要因・`goal-lifecycle-fork`）。期間表示は `Day N/M`（M=`end_day − start_day + 1`）。作成時は `end_day = start_day + 29` 固定。
- 「終える」は既に存在する（`goal-lifecycle-fork`）。永続ルールを `status='removed'` としてゲートから外し、目標をアーカイブし、レポート・沿革・カレンダーは残す。**ただし完走後（`today > end_day`）にしか押せず、理由は任意**。
- `goal.purpose`（目的の一文）は既にあり、カードに `gr-purpose` として表示されている。
- グループの束ね規則は「**名前＋色 identity**」で確立済み（`today-group-breakdown` / `reflection-day-overview`）。`stable_group_id` が入れ替わっても分裂しない。
- ⑤沿革（`goal-chronicle`）は「1つの目標の中のルール操作と凍結イベントの年表」。
- 削除は作成当日のみ（`goal-challenge`）。

**issue #76 の診断**: 詳細は `proposal.md` の Why を参照。要求のほとんどは既存資産の解放で満たせ、新規は「目標時間」ひとつである。

## Goals / Non-Goals

**Goals:**
- 「1日あたり何時間」という、**日次ゲートには原理的に乗らない**目標を、乗せずに扱えるようにする。
- 目標タブを開いた瞬間に **現在地（いま何時間・あと何時間）** が読めるようにする。
- 期間を自由にし、**降りる手段**を与える（未達で終わることを正当な選択にする）。
- **目標時間を持たない目標を、例外分岐なしで同じ器に収める**。
- 既存資産（`end_day` の延長ロジック・「終える」・`purpose`・グループ identity・レポート・凍結）を**壊さずに解放する**。

**Non-Goals:**
- 新しい器（サイクル・週次エンティティ等）を作ること。**期限が可変になれば「週次」と「長期目標」は同じものである**。
- 目標時間を解錠ゲートへ合流させること（**設計の中核として禁止**。D3 参照）。
- レポート①の棒グラフ化・日別モーダル・振り返りを後から埋める導線（**次の change**）。
- 大きい沿革の横スクロールUI（中身が先・見た目は後）。
- `< >` による目標の前後ナビ。
- 目標時間を1目標につき2つ以上持つこと。
- 期限の**短縮**手段。
- ルール・ゲート判定・凍結・⑤沿革・Before/After の仕様変更。

## Decisions

### D1: 目標時間は `goal` に高々1行ぶら下がる。束ねる対象は member テーブルで持つ

```
goal_target_hours(goal_id PK, kind{TOTAL_WORK,GROUP_SET,TIMELINE},
                  seconds_per_day, label_snapshot, created_at)

goal_target_hours_member(goal_id, ref, ord)
    -- kind=GROUP_SET のとき group identity を1件以上
    -- kind=TIMELINE  のときカテゴリラベルを1件
    -- kind=TOTAL_WORK のとき member 行を持たない
```

`goal_id` を PK にすることで「1目標に最大1つ」がスキーマで保証される。2つ以上の目標時間を並行させたい場合は**2つの目標を立てる**（`ユーザーフロー.md`「今回やらないこと」）。それぞれが独自の「目標とする状態」と期限を持つほうが、1つの目標に無関係な時間目標を同居させるより意味が通る。

`ref` は既存の安定キーの流儀に従う（`group:<identityId>` / `timeline:<ラベル>`）。**ルール（`rule:<id>`）を指してはならない**：目標時間は下限ルールの有無と独立に立てられる必要があるため（例: 下限ルールが無いグループにも目標時間を置ける）。

`ord` は表示順の決定性のために持つ（`アルゴリズム ／ Python` の並びが毎回同じになる）。

**対象は作成時に固定** し、途中で足す／外す手段を提供しない。変えたくなったら**終えて作り直す**。理由: 途中で対象が変わると、ペースの分子が期間内で意味を変え、大きい沿革に載る「平均 1h51m / 2h」が何を指すのか読めなくなる。更新を許すより、終了と再作成のほうが**沿革が読みやすい**（issue #76 コメントのユーザー判断）。

### D2: 「or」＝ member の実測秒を単純加算する。二重計上は起きない

`kind=GROUP_SET` の実測秒は、member 各グループの当日実測秒の**単純和**とする。

```
accumulated(day) = Σ_{m ∈ members} groupSeconds(day, m)
```

グループ秒は **名前＋色 identity** で束ねた既存の集計（`today-group-breakdown` と同じ規則）を使う。同一の名前＋色は `stable_group_id` が入れ替わっても1つに合算されるため、束ねる側で重複を心配する必要はない。

異なる identity は互いに素な集計単位なので、単純和で二重計上は起きない。ただし**同じ identity を member に2回入れられないよう一意制約**を置く（`(goal_id, ref)` UNIQUE）。

### D3: 目標時間を解錠ゲートへ合流させない（`evaluate.ts` を触らない）

`goal_target_hours` は `per_condition_results` に**一切現れてはならない**。理由は2つあり、どちらも単独で決定的である：

1. **原理的に不可能**。「1日あたり」の達成はその日が終わるまで確定せず、期間平均としての到達は期限まで確定しない。当日評価・latch・`is_final` スナップショットのモデルと両立しない。
2. **思想的に有害**。目標時間をゲートに乗せると、それが実質の下限として振る舞い、「目標と下限」の二段構えが消えて「最低限をこなすだけ」に戻る（＝ issue #76 の症状そのもの）。

この禁止は spec に MUST NOT として書く。実装上は `evaluate.ts` に手を入れないことで自動的に守られ、`git diff -- server/src/rules/evaluate.ts` が空であることを最終確認に含める（tasks 参照）。

なお UI 文言は「パスワードの条件になりません／なります」で統一する（issue #76 コメントの指摘）。「ゲートに効く／効かない」という内部語彙を画面に出さない。

### D4: ペースの算定。分母は経過日数、凍結日は除く

```
elapsedDays = （start_day から min(today, 実効 end_day) までの日数・今日を含む・凍結日を除く）
accumulated = Σ 対象の実測秒（同じ範囲）
average     = accumulated / elapsedDays
todayRemain = max(0, seconds_per_day × elapsedDays − accumulated)
```

- `accumulated` は**今日の実測を含む**。これにより `todayRemain` は「今日あと何時間やれば到達するか」になり、毎日変わる。
- **凍結日は分母から除く**（`goal-freeze`）。凍結日はその目標にとって無かった日であり、レポートの達成日数が凍結日を分子にも分母にも入れない既存規則と一致させる。今回は目標時間が `goal` に直接ぶら下がるので、この整合が自然に取れる（`goal` と独立した器を作らなかったことの利点）。
- 到達済み（`todayRemain === 0`）は数字を出さず到達した旨のみを示す（追い立てない）。
- `elapsedDays === 0`（開始前・全期間が凍結）のときはペース表示を出さない。

実測秒の取得元：

| kind | 取得元 |
|---|---|
| `TOTAL_WORK` | 日次サマリの総作業秒（`countsTowardTotal` の扱いは既存どおり） |
| `GROUP_SET` | 名前＋色 identity で束ねたグループ秒の member 和（D2） |
| `TIMELINE` | 当該カテゴリの `activity_log_entry`（MANUAL）持ち分秒 |

### D4-b: 到達判定は期間平均。「N日超えた」は採らない

目標時間の到達/未達（レポート・大きい沿革に載る値）は **`average >= seconds_per_day`** で判定する。「1日あたりの目標を超えた日が N 日」という数え方は採らない。

理由: ペース表示（`todayRemain`）と到達判定を**同じ式**にすることで、画面に出ている数字と、後から沿革で読む判定が食い違わない。日数カウント方式にすると「今日あと何時間で到達か」が定義できなくなる（今日を超えても、過去の未達日は取り返せないため）。

**割り切り**: 1日だけ大量にやって平均を作ることが可能である。下限ルール（毎日15分など）がその歪みを部分的にしか抑えないことは受け入れる（Risks 参照）。

### D4-c: めざす状態と証拠写真。判定はせず、自己申告と写真を並べて残す

```
goal.purpose          -- 「めざす状態」。任意 → 必須へ昇格。カードに常時表示
goal.outcome_caption  -- 証拠写真のキャプション。NULL なら「求めない」
goal.outcome_met      -- 終わるときの自己申告。NULL=答えない / 1=できた / 0=できなかった
```

**新テーブルを足さない。** 証拠写真の実体は既存の `goal_image`（`goal_id`＋`day_key`＋キャプション）であり、`outcome_caption` は「どのキャプションが証拠写真か」を指すポインタにすぎない。

これにより次がすべて自動的に成立する：

- **初期写真（Before）** … 作成フォームの既存ステージング機構（`goals.js` の `buildCreateImageStager`）で `outcome_caption` を固定キャプションとして Day1 に保存する。
- **終了時の写真（After）** … 同じキャプションで当日 `day_key` に保存する。
- **レポート③** … キャプションでグループ化して最古/最新を並べる既存実装が、**何も変えずに正しい Before/After を描く**（`goal-report ③` の仕様は変更しない）。

`outcome_met` は **3値（NULL / 0 / 1）** とし、必須にしない。「アルゴリズムを一通り実装できるようになったか」は白黒つかないことがあり、必須にすると嘘の自己申告を強制する。**答えないことも事実**として記録する。

**これは採点ではない。** システムは写真も文章も検証せず、本人の申告をそのまま残すだけである（既存の `MANUAL_CHECK` と同じ名誉ベース）。したがって既存の「合格・不合格・スコアに相当する表示を持ってはならない」に抵触しない。

**`✓` / `×` の扱いは画面によって分ける（D7-b）。** 大きい沿革では `×` を使ってよく、それ以外（レポート①〜⑤・目標カード・今日タブ）では従来どおり使わない。

### D5: 期限は作成時に自由指定。ただし短縮手段は依然として持たない

`POST /api/goals` が `endDay` を受け取る。`endDay >= start_day` を検証する（同日＝1日の目標も許す）。1週間/2週間/30日のボタンは**クライアント側の入力補助**であり、サーバーは日付だけを見る。

既存の「`end_day` は前方向にのみ動く」不変条件（`goal-lifecycle-fork`）は**そのまま維持**する。作成後に期限を早める API を提供してはならない。短くしたい要求（「試験勉強はもう大丈夫」）は D6 の「終える」が受ける。

理由: 短縮を許すと、ゲートが厳しい日に期限を今日へ縮めて逃げる経路が、**理由も記録も残さないまま**開いてしまう。終了（D6）は理由必須で大きい沿革に残るので、**降りる手段を1つに絞り、そこに理由と記録を集中させる。**

### D6: 「終える」を進行中へ広げ、理由必須にする。発効は**当日**

既存の完走フォークの「終える」処理を再利用し、発火条件を広げる：

```
                  変更前                    変更後
  発火できるとき   完走後のみ                いつでも（進行中・完走後）
  聞くこと        理由（任意）               ①めざした状態の答え（3値・任意）
                                            ②証拠写真（任意・outcome_caption があるときのみ）
                                            ③理由（必須・空は 400）
  効き始め        当日                      当日（変えない）
  ルール          永続ルールを removed       同じ
  レポート・沿革   残す                      同じ
  焼き込み        なし                      final_pace_json ＋ outcome_met
```

**進行中の終了と完走の「終える」で問いを分けない。** どちらも同じ3つを聞き、どちらも当日から効く。分岐を作ると「完走したときだけ状態を聞かれない」といった非対称が生まれ、大きい沿革の行の形が揃わなくなる。

**当日発効にする理由**（検討の末、翌日発効案を取り下げた）：

1. **既存の確立した原則と一致する**。`editable-rule-registry` は「ルールはいつでも追加・変更・削除でき**当日から効く**」と定めている。目標を終えることは、その目標の永続ルールをまとめて削除することに等しい。単体のルール削除が当日効くのに、目標終了だけ翌日というのは筋が通らない。
2. **抑止は記録が担う**。ゲート回避目的で目標を終えれば、その事実・理由・そのときの未達が**大きい沿革に永久に残る**。仕掛けで塞ぐのではなく逃げた事実を歴史に残すのが本アプリのやり方であり（凍結・理由つき緩和を「消してはならない」）、ここだけ仕掛けで塞ぐのは一貫しない。
3. 翌日発効は完走後の「終える」にも波及し、**既存の即時挙動を後退させる**副作用があった。

実装は `goal.ended_day_key = today` を持ち、`today >= ended_day_key` の目標を終了扱いとする（将来日付を入れる余地は残るが、現時点で書くのは当日のみ）。

**凍結との相互作用**: 凍結中／凍結予約中の目標を終えた場合、予約は取り消し、凍結による `end_day` 延長は既に適用済みのぶんを残す（過去の事実を書き換えない）。凍結の沿革エントリは消さない。

### D7: 大きい沿革は導出。専用テーブルを持たない

「これまでの目標」の各行は、`goal` テーブルと `goal_target_hours`、および終了時に焼き込んだ結果から**導出**する。イベント専用テーブルを新設しない。

```
＋作成   … start_day、name、purpose（めざす状態）、start_reason（なぜ始めるのか）、
            目標時間、初期写真（あれば）
−終える  … ended_day_key、end_reason、final_pace_json の到達/未達、
            outcome_met（めざした状態の答え）、Before→After の写真
✓完走   … 実効 end_day を越えた日、完走時点の到達/未達、outcome_met、写真
```

`start_reason` は本 change で新設する（`goal` に列を追加）。**必須**とする理由: 本アプリはルールの追加・変更・削除がすべて理由必須であり、目標そのものだけ理由なしで始められるのは一貫しない。加えて、大きい沿革で `＋作成 ― 理由` と `−終える ― 理由` が**対**になって初めて「なぜ始めて、なぜやめたか」の年表として読める。`purpose`（めざす状態＝**何**）と `start_reason`（**いま何故**）は役割が違うので、片方で代用しない。

並びは `day_key` 昇順（同日内は `id` 昇順）で**決定的** SHALL。到達/未達は**終了・完走の時点で焼き込む**（`goal.final_pace_json`）。後からグループを改名しても数字が動かないようにするためで、`goal-report ②` が評価時の焼き込み値で描くのと同じ理由による。

写真は `outcome_caption` に一致する `goal_image` を `day_key` 昇順で引き、**最古を Before・最新を After** として並べる（レポート③と同じ解決規則を使い、独自のグループ化を持たない）。

**大きい沿革の主役は「3つが並ぶこと」である。** 目標時間（数字）・`outcome_met`（自己申告）・写真（証拠）が同じ行に揃って初めて、「時間は足りなかったが状態には届いた」「時間は足りたが状態には届かなかった」という**数字だけでは読めない事実**が読める。どれか1つでも欠けている行（目標時間なし・写真なし・未回答）は、欠けたまま表示する（埋めない・美化しない）。

### D7-b: `✓` / `×` は大きい沿革でのみ使う

大きい沿革の到達・未達および `outcome_met` は、**`✓` / `×` で一目で見分けられるように示してよい**。他の画面（レポート①〜⑤・目標カード・今日タブ）には持ち込まない。

理由: 大きい沿革の用途は「並べて眺めて次の一手を考える」ことであり、**`×` が一目で拾えないとその用途自体が成立しない**。目標に達しなかったのなら原因があり、それを潰せばよいだけで、**判定は診断であって断罪ではない**（本人の言葉:「僕的には全然ポジティブな失敗判定」）。

禁止線は動かさない。依然として出してはならないもの: **合格・不合格・スコア・点数・ランク・紙吹雪・バッジ**。出してよいのは `到達 / 未達`・`できた / できなかった` という**事実の2値**と、それを見分けるための記号だけである。

この線引きが必要なのは、`×` を全画面に配ると今日タブのゲートやレポート①が「今日の自分に×が付く画面」になり、無採点の背骨が実質的に崩れるためである。大きい沿革は**過去を俯瞰する場所**なので、そこだけ記号を許す。

### D8: 画面の置き場所

- **作る／現在地を読む／終える** ＝ 目標タブ（既存の「読む＝目標タブ」の分業に従う）
- **大きい沿革** ＝ 目標タブのカード一覧の**下**（issue #76 コメントの「レポートがたくさんある感じの画面の下」がここ）
- **気づく** ＝ 今日タブ最上部の1行（毎日必ず開く場所に入口を置く。本体は置かない）

振り返りタブへは何も置かない。振り返りタブは**対象日**を単一所有するワークスペース（`reflection-timeline-workspace` design D2）であり、期間単位の表示は日付ストリップの意味論と衝突する。

## Risks / Trade-offs

- **平均方式は「1日だけ大量にやって平均を作る」ことを許す**（D4-b）。下限ルール（毎日15分など）がその歪みを部分的にしか抑えない。ペース表示との一貫性を優先した意図的な割り切りだが、実際に「最終日にまとめて」が常態化するようなら日数カウント方式を再検討する。
- **期限を自由にしたことで、目標が乱造されうる**。上限を設けていないので「300日」も「1日」も作れる（上限は「困ったら足す」判断）。1日の目標は平均＝実測になり、目標時間の意味がほぼ消える。大きい沿革が短命な目標で埋まるようなら床を検討する。
- **`✓` / `×` の解禁が滲み出す危険**（D7-b）。大きい沿革だけの扱いと決めたが、実装上は同じ到達判定の値を使い回すため、コンポーネントを共有した瞬間にレポートやカードへ `×` が漏れる。**画面ごとに表示を分ける責務をどこに置くか**（サーバーが記号を返さない／クライアント側で沿革だけが記号を付ける）を実装時に決め切る必要がある。ここを外すと、今日タブが「自分に×が付く画面」になり無採点の背骨が実質的に崩れる。
- **`outcome_met` が「無採点」の原則を侵さないか**。本人の自己申告であり、既存の `MANUAL_CHECK` と同じ名誉ベースなので理屈は通っている（D4-c）。ただし**画面上は「できた／できなかった」というラベルが目標に付く**ことになり、体感として合否に近づく余地は残る。
- **当日発効にしたことで、ゲート回避目的の終了が技術的には可能になる**（D6）。抑止は大きい沿革に事実が残ることだけであり、システム的な歯は無い。本アプリの既存の思想（逃げた事実を記録に残す）に沿った選択だが、**記録を気にしなくなった時点で歯が消える**ことは受け入れる。
- **`outcome_caption` を1目標に1つしか持てない**。「体・正面」と「体・横」の両方を証拠にしたい目標は表現できない。既存の `goal_image` はキャプションが自由なので振り返りタブから手動で追加はできるが、大きい沿革には載らない。
- **証拠写真を出さずに終える経路が普通にある**（任意なので）。大きい沿革の行に写真が無いことは頻繁に起きる。「欠けたまま表示する」方針だが、欠けた行が多いと沿革がスカスカに見える可能性がある。
- **目標時間と下限が別物であることが伝わるか**。フォーム上は隣り合う2つの欄で、片方は「パスワードの条件になりません」、もう片方は「なります」と書くだけ。issue #76 コメントで文言の分かりにくさが既に指摘されており、**ここが伝わらないと二段構えの意味が失われる**。
- **大きい沿革の作成理由が未決**（D7 ❓）。`purpose` で代用すると「なぜ始めたか」ではなく「何を目指すか」が載ることになり、終了理由（「試験勉強はもう大丈夫」）と対にならない。
- **既存の30日目標との後方互換**。`goal_target_hours` を持たない既存の目標は、ペース表示が出ないだけで従来どおり動く必要がある。既存の `end_day = start_day + 29` のデータもそのまま有効。
- **デモモードの決定性**。ペース表示は「今日」に依存して数字が動くため、デモの仮想日付を分母に使う経路を通す必要がある。サンプルは固定 `day_key`／固定タイムスタンプで焼き込み、既存の達成 24/30・中盤の谷の筋書きを壊さない位置へ寄せる。
