## Context

`goal-blueprint`（タスク一覧）は `goal-blueprint-task-tree` でツリーを持ち、`task-list-inline-edit` で編集できる面になった。残っている穴は2つ:

1. **階層を変える手段が画面に無い**。`setParent(db, taskId, parentId)` は循環検査つきで実装済みだが、叩く UI が無い。取り込み先を指定する「まとめて追加」で回避していたが、それは「入れる場所を先に決める」形で、**組みながら直す**作業には合わない。
2. **編集がすべてマウス**。行にホバー → `＋` → 入力 → Enter → Esc → 次の行へホバー。骨組みを一気に打ち込めない。

design doc（`Task Tree.dc.html` の t1/1b）は実際に動く試作で、この2つをアウトライナーのキーボード操作で解いている。t2/2a はカンバン側で、カード上端の色付き帯に「目標 / 親タスク」を出す。

**現行実装の当たり所**（調査済み）:

| 対象 | 現状 |
|---|---|
| `server/static/js/blueprint.js` (449行) | `.bp-node-row` のプレーン行。`S.renamingId` / `S.addTarget` / `S.bulkTarget` / `S.menuOpenId` |
| `server/static/css/app.css` 1439〜1483 | `.bp-*`。**1ルール1行のコンパクト書式** |
| `server/static/css/app.css` 601〜603 | `.kb-breadcrumb` / `-text` / `-sep`。本文上のグレー1行 |
| `server/static/js/kanban.js:789` | `parentBreadcrumbEl(t)`。`S.tasks` から直近の親を引くだけ |
| `server/src/services/task-tree.ts` | `setParent` / `createChildTask` / `createRootTask` / `startBranch` / `dropBranch` / `getBlueprint` |
| `server/src/api/planning.ts:150` | `POST /api/tasks/:id/children`。`PATCH /api/tasks/:id` の `parentTaskId` は `setParent` を通す |
| カンバンと目標の関係 | **無い**。`kanban.js` に `goal` の語が1つも出てこない |

## Goals / Non-Goals

**Goals:**

- タスク一覧を**キーボードだけで組める**面にする（Enter / Tab / Shift+Tab / Alt+C / ↑↓ / Ctrl+Enter）
- 進捗の総量（葉ベース）と、いま触っている行が**目で分かる**ようにする
- カンバンのカードが**どの枝のものか**、盤面を見ただけで分かるようにする
- 既存の API 資産（`setParent` の循環検査・`createChildTask` の完了済み拒否）を**再実装しない**

**Non-Goals:**

- ドラッグによる並べ替え・再親付け（モックの凡例にはあるが今回は入れない。別 change）
- 兄弟どうしの並べ替え（`tree_order` の入れ替え）。`Tab` / `Shift+Tab` は**深さを変える**操作だけを扱う
- カンバン側の配色・列・カード構造そのものの変更（帯だけを触る）
- タスク一覧からのカテゴリ付与

## Decisions

### D1: パンくず帯の「親」は**直近の親**にする（根の枝ではない）

design doc の t2 は「コースを決める」の帯に「運動を習慣にする」を出しており、根の枝を指しているように読める。だが**同じモックの中で「朝の散歩を20分」自体もカード化されている**（＝子を持つのにカードになっている）ので、モックが自己矛盾している。

既存 spec `task-tree`「カードは親のパンくずを表示する / 深いツリーでも親は1つだけ」は**直近の親**を規定しており、変える理由が無い。ツリーを「どのカードも葉」に整え直せば直近の親＝根の枝になり、モックと同じ絵になる（`ref/goal-blueprint/kanban-crumb-mock.html` はそう描いた）。

**却下した案**: 根の枝を出す。深いツリーで「目標 / 最上位の枝」しか出ず、直近の文脈（何の一部なのか）が消える。パンくずの目的に反する。

### D2: 帯の色は**根の枝の `task.id`** から決定的に引く

モックは同じ目標の中で緑 / 青 / 紫の3色を使い分けている。目標ではなく**枝**が単位。色の決定は次のとおり:

- 色パレット = design doc の3色（緑 `#E9F5EE`/`#CFE7D8`/`#2E7D54`、青 `#E7F0FA`/`#D3E3F5`/`#2C5C8C`、紫 `#F3F0FA`/`#E2DBF2`/`#5B4A9A`）
- キー = そのカードが属する**根の枝のタスク id**（`root_task_id`）。`root_task_id % 3` でパレットを引く

**却下した案A**: 根の枝の表示順（`tree_order`）で引く。3枝なら必ず3色に散って絵は綺麗だが、**並べ替えると色が変わる**。カードの色が理由なく入れ替わるのは、記憶の手がかりとして使えない。
**却下した案B**: `manual-category-registry` の `GROUP_COLORS`（`util.js`）を使う。あれはタブグループの色名→hex の写像で、任意のキーから引く仕組みではない。帯は3色の淡いトーンで揃える必要があり、9色のビビッドな値をそのまま使うと帯として成立しない。

id 剰余なので隣り合う枝が同色になることはある。**色は補助**（枝の同一性のヒント）であって識別子ではない、と割り切る。名前は必ず帯に書いてある。

### D3: 目標名は `listTasks` に再帰 CTE で載せる

カンバンには目標の情報が1つも渡っていない。フロントで根まで辿って別 API を叩くのは往復が増える。`listTasks` の SELECT に再帰 CTE を足し、**各タスクの `root_task_id`** と、その根の `goal_id` から引いた **`goal_name`** を返す。D2 の色キーもこれで同時に手に入る。

目標に属さない根（`POST /api/tasks` で直接作ったタスク）の子は `goal_name` が `NULL` になる。そのときは**帯に親だけを出し、区切りの `/` も出さない**。

**却下した案**: `kanban.js` が `GET /api/goals` も読んで突き合わせる。目標は数十件でも、根→目標の対応をフロントで作り直すことになり、`listTasks` が既に `has_children` を載せている先例（`design D3`）から外れる。

### D4: 階層操作の当たり先は `PATCH /api/tasks/:id/tree-position` 1本

`Tab` と `Shift+Tab` は「親を変えて、決まった位置に置く」という同じ操作の2つの向きなので、エンドポイントを分けない。

```
PATCH /api/tasks/:id/tree-position  { parentId: number | null, afterTaskId: number | null }
```

- `Tab`（1段深く）: `parentId` = **直前の兄弟**、`afterTaskId` = その兄弟の末子（＝末尾に付ける）
- `Shift+Tab`（1段浅く）: `parentId` = **いまの親の親**（無ければ `null` ＝根）、`afterTaskId` = **いまの親**（＝親の部分木の直後に置く）

サービス側は `setTreePosition(db, taskId, { parentId, afterTaskId })`。`parentId` が非 `null` のときは**必ず `setParent` の循環検査を通す**（新しい検査を書かない）。`parentId` が `null`（根へ戻す）ときは、いまの祖先チェインを辿って根の `goal_id` を継ぐ（`deleteTask` の繰り上げ処理と同じ考え方）。部分木は `parent_task_id` の付け替えだけで一緒に動くので、子孫を触る必要は無い。

`afterTaskId` は `tree_order` の採番にだけ使う。**兄弟の並べ替え API ではない**（Non-Goals）。

**却下した案**: `PATCH /api/tasks/:id` の `parentTaskId` を使い回す。既に `setParent` を通す経路があるが、`setParent` は必ず**末尾**に置くため、Shift+Tab で「親の直後」に戻せない。位置指定が要る時点で別の口が要る。

### D5: `Enter` の当たり先は `POST /api/tasks/:id/siblings`

「対象の**部分木の直後**に、同じ深さで1件」。対象が根なら新しい根（`goal_id` を継ぐ）、そうでなければ同じ親の子。`createChildTask` と `createRootTask` の両方を内側で使い分ける `createSiblingTask(db, taskId, title)` を置く。

**新規タスクの `status`**: `createChildTask` は親の `status` を継ぐ。兄弟追加も**対象の兄弟と同じ `status`** を継ぐ。取り込み（`HOLD` 固定）とは別の操作なので、`HOLD` に落とさない。手で1件ずつ足すときに保留へ入るのは、`createRootTask` が `TODO` を作る現状とも食い違う。

**空タイトルは作らない**。モックは空文字の行を作ってから打たせるが、それだと「Enter を押しっぱなしで空タスクが増える」事故と、サーバ往復のたびに空行が残る問題が出る。**タイトルを打ってから Enter で確定**する現行の流儀（`bp-add-input`）を残し、`Enter` は「確定して、直後に次の入力を開く」にする。

### D6: 容れ物のチェックは `POST /api/tasks/:id/subtree-done`

`setSubtreeDone(db, taskId, done)`。対象の**部分木にある葉**を一括で `DONE` / `TODO` にする。

- **打ち切り済み（`drop_reason` が非 NULL）の葉は動かさない**。打ち切りは決着済みで、外すと理由が消えるか、理由を持ったまま未着手に戻るかのどちらかになり、どちらも壊れている。
- 容れ物の完了は従来どおり**子から導出**する（`getBlueprint` の `build()`）。`task` 行に容れ物の完了を書かない。押せるようになるのは**入口**だけで、導出規則は変えない。
- `Alt+C` も葉・容れ物を問わずこの1本を叩く（葉なら部分木＝自分1つ）。

**却下した案**: フロントから葉の数だけ `PATCH /api/tasks/:id` を投げる。20葉の枝で20往復。途中で失敗すると半端な状態が残る。

### D7: タイトルは常時 `<input>`。確定は blur / Enter、`Escape` で戻す

`task-list-inline-edit` で入れたダブルクリック改名（カンバンの `cardTitleEl` の流儀）をやめる。理由は D5 と地続きで、**キーボードだけで組む**ときにタイトルへ入るのにマウスが要るのは通らないため。

事故防止:

- 値が変わっていなければ保存要求を投げない
- **空文字は保存しない**（`Escape` と同じく元の値へ戻す）。空タイトルのタスクを作らせない
- `IME` 変換中の `Enter`（`e.isComposing` / `keyCode === 229`）は握り潰す。現行の `bp-node-title-edit` と同じ

### D8: 詳細モーダルは `md-editor.js` を使う

`Ctrl/⌘+Enter` で開き、`task.notes` を編集する。モックの `editorKey()` は「2スペース単位の Tab インデント」「`-`/`*`/`+`/`1.`/`- [ ]` の継続」を素の `<textarea>` へ手で実装しているが、**同じ挙動が `server/static/js/md-editor.js` に既にある**（`createMarkdownEditor` はカンバンのノートとまとめて追加で使用中）。モックの JS を移植せず、既存エディタを埋める。

パンくずは `目標名 › 祖先 › …` を ` › ` で連結（`getBlueprint` のツリーから組めるので新しい API は要らない）。`Esc` で閉じる。`↑↓` でモーダルを開いたまま対象を移動できるモックの挙動は**入れない**（保存の確定タイミングが読めなくなる）。

### D9: 再描画の粒度は現行のまま（`renderAll` で作り直す）

`blueprint.js` は毎回 DOM を捨てて作り直し、`focusActiveInput()` でフォーカスを戻している。キーボード操作が増えると「どの行のどこにキャレットがあったか」を戻す必要があるので、**選択中のノード id とキャレット位置を `S` に持ち、再描画後に復元**する形へ広げる。仮想 DOM を持ち込まない（このリポジトリに前例が無く、449行のビューのために導入する理由が無い）。

### D10: 撤去する UI と、その行き先。`⋯` は削除専用にして残す

| 撤去するもの | 行き先 |
|---|---|
| 行ホバーの `＋`（子を足す） | `Tab`。兄弟として足してから1段潜らせる |
| `⋯` >「まとめて追加」（取り込み先の指定） | ヘッダ右上の「まとめて追加」＝**根に足す**。既存の枝へ入れたければ足してから `Tab` |
| `⋯` >「保留の N 件を未着手へ」 | **無くなる**（サービスと API は残る） |
| `⋯` >「この枝を打ち切る」 | **無くなる**（サービスと API は残る） |
| `⋯` >「削除」 | **残す**（`⋯` は削除だけを持つ1項目のメニューになる） |

design doc の t1 には `⋯` が無いが、**削除だけは意図的に外れる**。理由は他の4つと性質が違うため:
ほかは代わりの入口がある（`＋` → `Tab`、取り込み先の指定 → まとめて追加＋`Tab`）か、
そもそもツリーを組む最中の操作ではない（着手・打ち切りは枝を選んで盤面へ流す判断）。
**削除だけは代わりが無い**。容れ物はカンバンに出ないので（`task-tree`「葉だけがカンバンのカードになる」）、
ツリーから消せないと `DELETE /api/tasks/:id` を直接叩く以外に手が無くなる。

`⋯` を残すことの費用は「行ホバーで1つボタンが出る」だけで、モックが避けたかった
**行ごとに操作が積み重なる**状態（撤去前は `＋` と `⋯` の2つ＋メニューに4項目）には戻らない。
**この方針を守るため、`⋯` に削除以外を足さない**ことを spec の MUST NOT として書いた。

## Risks / Trade-offs

- **[枝への着手・打ち切りの導線が画面から消える]** → 緩和していない。サービスと API は残るので機能は失われないが、**画面からは行えなくなる**。取り込み直後の葉が `HOLD` に入る以上、盤面へ流す操作はどこかに要る。今回は「タスク一覧はツリーを組む場所であって、盤面へ流す判断をする場所ではない」と割り切るが、**流す先が無いまま `HOLD` が溜まる**のが実運用で問題になったら、置き場所を別 issue で決める（候補は目標カードかカンバンの保留列のヘッダで、**タスク一覧の行へ戻さない**）。
- **[`⋯` に操作が再び溜まる]** → `⋯` を削除専用で残したので、次に「ここへ入れれば楽」という誘引が常にある。撤去前は `＋` と `⋯` の2つ＋メニュー4項目で、まさにそれが積み重なった結果だった。spec に「メニューに入れてよいのは削除だけ」を MUST NOT として書き、シナリオ「メニューには削除しか入っていない」で機械的に見張る。
- **[常時 `<input>` で誤編集が起きる]** → D7 の3つのガード（無変更なら投げない・空文字は戻す・IME 中の Enter を無視）。それでも「クリックしたつもりが1文字消えた」は起こりうる。`Escape` が常に直前の値へ戻ることを凡例に出す。
- **[`Shift+Tab` で根へ戻したときに `goal_id` が抜ける]** → 根は `goal_id` を持つ必要がある（`getBlueprint` は `goal_id === rootGoalId` の根しか拾わない）。抜けると**そのタスクがタスク一覧から消える**。D4 で祖先チェインから継ぐと決め、vitest で凍結する。
- **[部分木の一括完了で打ち切りが壊れる]** → D6 で打ち切り済みの葉を対象外にし、vitest で凍結する。
- **[再帰 CTE で `listTasks` が重くなる]** → `listTasks` は盤面の描画のたびに呼ばれる。タスクは個人利用で数百件規模、`task(parent_task_id)` の索引があれば CTE は問題にならない見込み。**索引の有無を実装時に確認**し、無ければ足す。
- **[`＋` を消したのに `Tab` に気づかない]** → 凡例の帯を常時表示にし、`attachTooltip` を追加ボタン・チェック・キャレットへ併記する（プロジェクトルール）。それでも初見では気づきにくいので、**空状態の文言**で「Enter で足して Tab で潜らせる」を明示する。
- **[CSS の全面差分]** → `.bp-*` はほぼ総取り替えになる。`app.css` は1ルール1行の書式なので、**フォーマッタをファイル全体にかけない**。編集後に `git diff --stat -- server/static/css/app.css` の桁を確認する（前例: 1行の修正のつもりが 5,700 行差分になった）。

## Open Questions

- 帯の色パレットを3色のままにするか増やすか。枝が4つ以上ある目標では必ず色が重複する。今回は3色で出し、**実データで重複が邪魔になるかを見てから**増やす（増やすときは delta spec のパレット表を直す）。
- `Tab` で潜らせた先が**完了済みの容れ物**だった場合の扱い。`createChildTask` は完了済みの親を拒否するが、`setTreePosition` は既存タスクの移動なので同じ検査を通すべきか、通さないべきか。今回は**通さない**（移動は分解ではなく、完了済みの枝へ未完了の葉が入ると容れ物の完了が自動的に解ける ＝ 導出規則どおりで矛盾しない）。実装後に不自然なら別 issue。
