## Context

`server/src/config.ts` の `loadRuntimeConfig()` は port と dbPath を同時に、かつ実際に
バインドを試みる前に確定させている。`server/src/main.ts` はその結果を使って `openDb()` →
ルート登録 → `app.listen()` の順に起動する。ポートが衝突すると `app.listen()` が例外を投げ、
`main().catch()` でプロセスごと終了する(worktree での動作確認が「先に本チェックアウト側の
プロセスを止める」以外の方法で成立しない)。

`server/.env`(tracked)は `DB_PATH` を本チェックアウトの実 DB 絶対パスに固定しており、
`--env-file-if-exists` は「既に設定済みの環境変数は上書きしない」仕様のため、呼び出し側が
明示的に `DB_PATH=...` を渡さない限りこの値が常に勝つ。worktree はこの `.env` ごと
コピーされるため、worktree からの起動でも常に本チェックアウトの実 DB に接続してしまう。

また現状、ダッシュボードを見るには毎回手動で `npm run server` を実行する必要がある
(issue #13 タイトル)。この2つの要望は組み合わせて解決する: 本チェックアウトのサーバーを
Windows ログオン時に自動起動しておけば、いつものポートは常に本チェックアウトが握っている
状態になり、worktree からの起動は自然に「別プロセス・フォールバックポート・開発用 DB」
という扱いになる。

## Goals / Non-Goals

**Goals:**
- Windows ログオン時にサーバーが自動起動し、`npm run server` を手動実行しなくてもダッシュ
  ボードが使える状態になっている(非表示・バックグラウンド)。
- 自動起動の登録/解除は、リポジトリ同梱のセットアップスクリプトを一度実行するだけで完結する
  (追加の npm 依存を増やさない・再実行しても安全)。
- いつものポートが使用中でも `npm run server` がクラッシュせず、空きポートで起動できる。
- 「いつものポートで起動できた(＝競合なし)」場合は現状どおり実 DB に接続する。
- 「フォールバックした(＝競合あり、恐らく worktree からの動作確認)」場合は自動的に
  隔離された開発用 DB に接続し、実データへ書き込まない。
- 明示的な `DB_PATH` 指定(既存のデモ検証フロー: `PORT=<空きポート> DB_PATH=:memory: npm run server`)
  は今までどおり最優先で効く。
- 開発用 DB を新規作成した回に限り、最小限のサンプルデータ(カンバンタスク・長期目標)を
  投入し、空のダッシュボードではなく触って確認できる状態にする。
- 起動したポート番号とどちらの DB に繋がっているかを、ログを目視するだけで判別できる形で
  出力する。

**Non-Goals:**
- 拡張機能(extension)側の自動ポート追従(拡張は引き続き固定ポート前提。フォールバックは
  「人がブラウザ/API で手動確認する」用途に閉じる)。
- ポート探索範囲・再試行ロジックの高度な設定化(環境変数での上限変更など)。固定値でよい。
- デモモード(`server/src/services/demo-seed.ts`, `:memory:`)との統合。デモモードは既存どおり
  明示 `DB_PATH` 指定で完全に独立して動く。
- 「ログイン画面より前のシステム起動時」に起動する Windows サービス化(要管理者権限・要
  クレデンシャル保存)。今回は「ユーザーログオン時」の自動起動で十分とする(ユーザー確認済)。
- マルチユーザー環境・複数PCへの配布(単独開発者のローカル PC 1台を前提とする)。

## Decisions

### D1: ポート探索は「Fastify の listen をリトライ」ではなく「事前プローブ」
`app.listen()` 失敗後に同一 Fastify インスタンスへ再度 `listen()` することの安全性は保証
されていない。代わりに `net.createServer()` で試験リッスン→即クローズを行う純粋関数
`findAvailablePort(basePort, host, maxAttempts)` を用意し、DB を開く前に実ポートを確定する。
これにより「確定ポート」と「DB オープン」を疎結合な同期ステップとして扱え、vitest で
"占有中のポートを渡すと次の空きポートを返す" ことを実プロセス起動なしにテストできる。

- 探索範囲: `basePort` から最大 20 個(`basePort .. basePort+19`)。全滅したら明示的な
  エラーメッセージで `process.exit(1)`(現状の「クラッシュする」という失敗モード自体は
  維持しつつ、理由を分かりやすくするだけに留める)。

### D2: DB パス解決の分岐条件は「実際にバインドできたポート ≠ いつものポート」
「worktree かどうか」を直接判定するのではなく、「フォールバックが発生したか」を条件にする。
理由:
- worktree かどうかの判定(cwd がメインチェックアウトと違う、`.git` がファイルかどうか等)は
  余計な複雑さを持ち込む上、本チェックアウト内で二重起動して動作確認したいケースを拾えない。
- 「いつものポートを取れなかった」という事実は、それだけで「別の常駐インスタンスが既にいる
  可能性が高い＝実 DB に相乗りすべきでない」という十分なシグナルになる。

解決順位(`resolveDbPath`という純粋関数として実装):
1. `process.env.DB_PATH` が設定されていればそれ(明示指定、最優先)
2. `config.local.json` の `dbPath` があればそれ
3. どちらも無い場合:
   - `actualPort === basePort` → `<serverRoot>/data/track.sqlite`
   - `actualPort !== basePort` → `<serverRoot>/data/track.dev.sqlite`

`serverRoot` は起動したプロセス自身のソース位置から解決するため、worktree で実行すれば
自然にその worktree 配下の `data/` を指す(cross-checkout の絶対パスを一切ハードコードしない)。

### D3: `server/.env` の `DB_PATH` 行を削除する(D2 と対になる決定)
このハードコードが「worktree でも実 DB に繋がる」という issue #13 の問題そのものの原因の
ため、除去は必須。除去後の本チェックアウト側の挙動は変わらない: `serverRoot` が本チェック
アウトの `server/` を指すため、D2 のデフォルト解決が結局同じ絶対パスに解決される
(`<repo>/server/data/track.sqlite`)。

### D4: 開発用 DB のサンプル投入は「ファイルが存在しなかった時だけ」実行
`openDb()` を呼ぶ前に `existsSync(resolvedDbPath)` を見て「新規作成かどうか」を判定する
(`:memory:` は対象外)。新規作成 かつ dbPath が `track.dev.sqlite` の場合のみ、
`openDb()` 完了後に `seedDevSample(db)` を呼ぶ。

`seedDevSample` は生 SQL ではなく既存のサービス関数(`createTask`, `createGoal` 等)を
呼んで投入する。理由: `demo-seed.ts` は「固定 day_key で再現可能な集計結果」を作るために
意図的に生 SQL で細部を制御しているが、開発用サンプルはそのような再現性要件が無く、
サービス関数のバリデーション・不変条件に自動的に追従できる方が壊れにくい。
中身は最小限(カンバンタスク数件+長期目標1件)とし、`Date.now()` 基準の相対的な日付で良い
(このデータは使い捨てで、再起動のたびに固定シナリオを再現する必要はない)。

### D5: 起動時ログは pino の info ログに加えて `console.log` で明示バナーを出す
Fastify の pino ロガーは JSON 1行ログのため、ターミナルで目視しづらい。「見えるようにしたい」
という要望に直接応えるため、`app.listen()` 成功後に以下のような平文行を追加で出す:

```
▶ track-and-control-me backend: http://127.0.0.1:<port>  [db: track.sqlite]
▶ track-and-control-me backend: http://127.0.0.1:<port>  [fallback port; db: track.dev.sqlite]
```

### D6: 自動起動はタスクスケジューラ(ログオン時トリガー)＋ vbs 非表示ランチャー
Windows でユーザーログオン時に非表示でコマンドを起動する定番手段として、以下を採用する:

1. `server/scripts/start-hidden.vbs` — `WScript.Shell.Run` の第2引数 `0`(ウィンドウ非表示)
   `False`(完了を待たない)を使い、リポジトリ直下で `npm run server` を起動する。
   `pwsh -WindowStyle Hidden` 単体では起動時に一瞬コンソールが見えることがあるのに対し、
   vbs 経由の `Run(..., 0, False)` は確実に非表示にできる(Windows での既知の手法)。
2. `server/scripts/register-autostart.ps1` — `Register-ScheduledTask` で上記 vbs を
   `wscript.exe` 経由に起動するタスクを作成する。トリガーは `New-ScheduledTaskTrigger -AtLogOn`
   (現在のユーザーがログオンした時。管理者権限・パスワード保存は不要)。
3. `server/scripts/unregister-autostart.ps1` — 対になる解除スクリプト
   (`Unregister-ScheduledTask -Confirm:$false`)。

タスク名は固定(例: `TrackAndControlMe-AutoStart`)にし、`register-autostart.ps1` は
既存タスクがあれば一度削除してから再登録することで冪等にする(パスを変えて再実行しても
古い登録が残らない)。

追加の npm 依存(`node-windows` 等でのサービス化)は採用しない。ユーザーはユーザーログオン時
起動で十分と回答しており、OS 標準機能だけで完結する方がメンテナンスコストが低い。

**実測での訂正**: 上記「管理者権限不要」は理論上の前提だったが、実機では非昇格(非管理者)の
PowerShell セッションから `Register-ScheduledTask` を実行すると「アクセスが拒否されました」で
失敗した(このマシンのアカウントはローカル Administrators 所属だが、セッション自体が UAC で
非昇格だったため)。PowerShell を「管理者として実行」で開き直せば登録できることを確認済み
(tasks.md 6.4 参照)。そのため `register-autostart.ps1` は実質「初回登録時のみ管理者権限の
PowerShell で実行する」運用とする(登録されたタスク自体はログオン時に自動実行されるため、
日常的な起動そのものに管理者権限は不要)。

### D7: 自動起動プロセスは「いつものポート」の占有役、worktree 側は port-fallback で共存
自動起動される本チェックアウトのプロセスは D1〜D5 の通常経路(いつものポートで起動 → 実 DB)
を通る。worktree からの手動 `npm run server` は、いつものポートが自動起動プロセスに
既に使われているため必然的にフォールバックポート＋開発用 DB 側に回る。つまり自動起動
(D6)と port-fallback/dev-db(D1〜D5)は同じロジックの上でそのまま共存し、worktree 用に
特別な分岐を追加する必要はない。

## Risks / Trade-offs

- [Risk] 開発用 DB 初回作成時にサーバープロセスが並行して2つ以上、同時にフォールバック
  ポートへ起動されるレース(ファイル存在チェックと作成の間に競合)
  → 単一開発者・手動起動が前提の用途であり、実務上ほぼ発生しない。発生しても
  「サンプルが二重投入される」程度の実害に留まる(実データ破損ではない)。許容する。
- [Risk] `server/.env` から `DB_PATH` を削除することで、"worktree から本物の実データを見たい"
  という(過去に .env hack が意図していた)ユースケースができなくなる
  → 明示的に `DB_PATH=<実DBの絶対パス>` を指定すれば今までどおり可能(D2 の 1 番目の優先
  順位)。自動でそうならない、というだけ。
- [Trade-off] ポート探索を「事前プローブしてから listen」にすることで、理論上は
  プローブ後・実 listen 前の僅かな時間に他プロセスが同じポートを奪う TOCTOU の余地がある
  → 単一開発者のローカル用途でほぼ無視できるリスク。実 listen が失敗したらそのまま
  プロセスを終了させれば十分(自動リトライまでは実装しない、Non-Goals 参照)。
- [Risk] タスクスケジューラ登録はリポジトリの絶対パスに依存するため、リポジトリを別の
  場所に移動した場合は登録し直す必要がある
  → `register-autostart.ps1` はスクリプト自身の位置からリポジトリルートを解決して
  登録するため、移動後にスクリプトを再実行するだけで直る(手動でパスを打ち直す必要はない)。
- [Risk] タスクスケジューラ・vbs という Windows 固有の仕組みであり、自動テスト(vitest)では
  検証できない
  → OS 統合部分(D6)は tasks.md の手動確認手順でのみ検証する。in-process のロジック(D1〜D5)
  は従来どおり vitest で検証する。
