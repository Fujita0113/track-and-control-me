## Context

`ユーザーフロー.md` が本変更の唯一の受け入れ基準である。この design はそれを実装に落とすための判断だけを書く。

前提となる既存の作り：

- `getGoalReport()`（`server/src/services/goals.ts`）は、①のマス目データ（`rep.rules[*].cells[i]`＝met/actualSeconds/thresholdSeconds/future/inactive/frozen）と、④の日別文面（`rep.days[i]`＝`{ dayKey, dayNumber, text, source: 'journal'|'reflection'|null, images }`。目標日記→振り返りの日単位フォールバック済み）を、**全日ぶん一括で**返している。
- フロント（`server/static/js/goals.js`）の `blockCalendar()` は、ヘッダの Day 番号（`.gr-cal-dh`）とルール行のセル（`.gr-cell`）の両方に `click` → `rs.renderReader(dayNumber)` を登録している。`renderReader` は④のセレクタ値・①のハイライト（`.sel`）を更新し、④の本文（読み取り専用）を描画するだけ。
- 気分（`satisfaction`, 1..5, NULL=未評価）は `reflection_entry` テーブルにあり、`GoalReport` には含まれていない（`rep.days` は文面とソースのみ）。
- 既存エンドポイント: `GET /api/summary?date=`（`daySummary`。グループ別実測秒）、`GET /api/reflection/:date`・`PUT /api/reflection/:date`（`{ content, satisfaction }`）。いずれもクライアント側 `api.js` に既存のラッパーがある（`getSummary` / `getReflection` / `putReflection`）。
- 目標日記（`goal_journal`）は目標が `active` のときだけ書き込める別の検証パスを持つ（`saveJournal`）。振り返り（`reflection_entry`）とは別テーブル・別バリデーションで、意図的に分離されている（issue #9 設計メモ: 「目標日記は reflection_entry と別テーブル」）。
- デモモード（`isDemo()`）はレポートを `api.demo.report(id, now)` から取得し、専用DB・仮想日付で動く。`GET /api/summary`・`GET/PUT /api/reflection/:date` に対応するデモ用エンドポイントは存在しない。

## Goals / Non-Goals

**Goals:**
- ①のマスから画面遷移なしで、その日の全体像（ルール達成状況・時間の内訳・気分・振り返り）を見られるようにする。
- 振り返りの書き忘れを、ネットワーク往復なしで高速に走査できるようにする（ホバー）。
- 振り返りをその場で（レポート画面から離れずに）書き直せるようにする。
- 既存データ・既存エンドポイントの再利用だけで実現し、新しい DB・API・サービスを持たない。

**Non-Goals:**
- ①達成カレンダーのグリッド自体の再設計（ユーザー判断により据え置き）。
- モーダルから目標日記（`goal_journal`）を編集すること。目標日記は別の検証パス（`active` のみ書込可）を持ち、今回のモーダルに混ぜると意味が曖昧になる。
- 複数日の一括編集。
- 未来日・凍結日・対象外日への新しい制限（既存の①クリック挙動をそのまま踏襲する）。
- デモモードでのモーダル対応（ホバーのみ）。
- 通知・リマインダーによる書き忘れの能動的な検知。

## Decisions

### D1: ホバーは新規データ取得をしない。`rep.days` を素通しする

ホバー時に表示するテキストは、レポート取得済みの `rep.days[dayNumber-1].text`（空なら「未記入」）をそのまま使う。**API 呼び出しを追加しない。**

理由: ①のマスは同時に多数（最大 M×ルール数）表示されており、マウス移動のたびに問い合わせるとサーバー・UI 双方に負荷とちらつきが出る。すでに手元にある `rep.days` は④が使っているのと同じ日単位フォールバック済みテキストであり、「その日書いたかどうか」を判定する目的には過不足ない。

### D2: モーダルは開くたびに、その日1件分だけ `GET /api/summary` と `GET /api/reflection/:date` を叩く

ホバーとは対照的に、モーダルは1日分だけを表示する操作なので、都度フェッチのコストは無視できる。**全日ぶんを先読みしない。**

- 時間の内訳（`GET /api/summary?date=`）は、②のグラフや今日タブが既に使っている集計をそのまま再利用する。目標に紐づかないグループの時間も含めて出す（issue の「何に何時間使って」に対応するため、ルールが張られているグループに限定しない）。
- 気分・振り返り本文（`GET /api/reflection/:date`）は `rep.days` の合成テキストとは別に、**生の `reflection_entry` の値**を取得する。`rep.days[i].source` が `'journal'` の日でも、振り返り本文自体は別に存在しうる（journal が優先表示されているだけで、reflection が空とは限らない）ため、編集対象は常にこちらの生データを使う。

### D3: 編集できるのは「振り返り」だけ。目標日記は読み取り専用の注記に留める

モーダルの保存ボタンは `PUT /api/reflection/:date` のみを呼ぶ。`rep.days[i].source === 'journal'`（その日、目標日記が優先表示されている）の場合、目標日記の本文をモーダル内に**読み取り専用**で追加表示し、「これは目標日記です。編集は振り返りタブ／目標コーナーから」の旨を添える。

理由: 目標日記（`goal_journal`）は `active` な目標にのみ書き込める別の検証パスを持ち、今回のモーダルに書き込み対応を混ぜると、目標の状態（終了・完走・凍結）ごとの分岐をモーダル側にも複製する必要が生じる。振り返りの編集だけに絞ることで、既存の `PUT /api/reflection/:date` の挙動（進行中かどうかを問わない）をそのまま使える。

### D4: 保存後はレポート全体を再取得して再描画する（差分更新はしない）

`PUT /api/reflection/:date` が成功したら、モーダルを閉じて `renderReport(root, goalId)` を呼び直す（既存の再描画経路をそのまま使う）。

理由: 保存によって `rep.days[dayNumber-1]` の `text`/`source` が変わりうる（例: 空だった日に本文を書いた）。この変化は①のホバー内容にも④の表示にも影響するため、両方を正しく更新するには全体再取得が最も単純で確実。1回の保存操作に対する追加コストは軽微であり、差分更新のロジックを持ち込んでバグを増やすより安全側に倒す。

### D5: クリック時、既存の④選択・ハイライト処理は変更せず、モーダルを追加で開く

`blockCalendar()` の `click` ハンドラ（ヘッダ・ルールセルの両方）に、既存の `rs.renderReader(dayNumber)` 呼び出しは残したまま、モーダルオープン処理を追記する。

理由: `goal-report④` の既存要求（「選択は①のマスのクリックまたは日付セレクタで行う」）を壊さずに済む。既存 e2e・spec のシナリオはそのまま成立し、モーダルは純粋な追加機能として載る。

### D6: デモモードではモーダルを開かず、ホバーのみ動かす

`isDemo()` が true のとき、クリックハンドラは既存の `renderReader` 呼び出しのみを行い、モーダルオープンをスキップする。ホバーのプレビューは `rep.days`（デモの report レスポンスにも含まれる）をそのまま使うため、分岐なしでデモでも動く。

理由: デモは専用DB・仮想日付（`now` パラメータ）で動作しており、本番用の `GET /api/summary`・`GET/PUT /api/reflection/:date` は対応していない（別の日付軸を参照してしまい、誤ったデータを表示・保存する危険がある）。デモに対応するエンドポイントを新設するコストに見合わないため、機能を絞る。

## Risks / Trade-offs

- **目標日記と振り返りが並んで見える混乱**: `source==='journal'` の日は、モーダル内に「振り返り（空かもしれない）」と「目標日記（読み取り専用）」の2つのテキストが並ぶ。これは既存のデータモデル（別物として意図的に分離）を正直に反映したものだが、初見では「なぜ2つあるのか」が伝わりにくい可能性がある。ラベルを明確にする以上の対策は今回取らない。
- **保存のたびにレポート全体を再取得する**: 対象日数が多い長期目標（延長された目標等）では、再取得のペイロードがやや大きくなる。体感できる遅延が出るようなら、次回以降で差分更新を検討する。
- **時間の内訳が「その日1日ぶんの目標時間」と比べる表示を持つ場合**（`ユーザーフロー.md` の未決❓）、目標時間は本来「期間平均」の指標であり、1日で切り取って比べることの意味は薄い。②のグラフに既に同じ水準線があるため認知の飛躍は無いと判断しているが、誤解を招くようなら表示を落とす。
- **デモでモーダルが開けないことの体験差**: デモ（読み取り専用ツアー）を使う人は、issue #76 の目玉である「振り返りをその場で編集する」体験を試せない。デモの位置づけ（お試しツアー・書き込みは目標コーナーの一部機能のみ許可）に合わせた妥当な制約と判断する。
