## Context

現状の `forecastMonth`（`server/src/services/kakeibo-forecast.ts`）は、1日平均を「今月これまでの日々の出費（特別費除く） ÷ 経過日数」の一本だけで出し、`ForecastMonthResult.series` を月初から月末まで1日刻みで返す。クライアント（`kakeibo.js` / `kakeibo-chart.js`）はこの `series` をそのままSVGの折れ線（実績は日ごとの段、予想は今日から先の直線）として描画しており、計算は一切クライアントで行っていない（`kakeibo-forecast/spec.md` の「予想はサーバで算出し、クライアントは描画に徹する」要件）。

この変更はUIモック（Artifact、issue #105）で3往復レビューして確定した内容を実装する。モックの数値・見た目は架空データだが、①基準トグルで1日平均の元データだけが変わり式自体は変わらないこと、②グラフは1枚のまま実績は不変で予想の破線だけが基準ごとに変わること、③滑らかな曲線・ゴースト線・直近7日ゾーンの帯・文字ラベルの絞り込み、④週ごとの支出は別要件として分析タブに独立配置、の4点は確定事項として扱う。

## Goals / Non-Goals

**Goals:**
- 月末予想の1日平均を「これまでの平均」「直近7日」の2基準から選べるようにし、両方をサーバで算出してクライアントへ返す（クライアントは選択と描画のみ）。
- 折れ線グラフを滑らかな曲線に描き直し、基準トグル・ゴースト線・直近7日ゾーンの帯を持たせる。
- 分析タブに月曜始まりの週次支出棒グラフ（週の目標線つき）を追加する。

**Non-Goals:**
- 月末予想の算出式（今日までの実績＋1日平均×残り日数＋予定出費）そのものは変えない。
- 特別費の判定ロジック（自動＝急な出費／手動除外）は変えない。
- 「今週の残り予算」は変えない。「無駄遣い」は集計ロジックは変えないが、ホームの表示文言は簡略化する（Decision 6）。
- 直近7日ベース予想と週ごとの支出の間にデータ依存は作らない（完全に独立した2機能）。

## Decisions

### 1. `forecastMonth` は2基準ぶんの1日平均・予想を1レスポンスで返す

サーバ側で `all`（既存の全期間平均）と `recent`（直近7日平均）の両方を計算し、`ForecastMonthResult` に両方を含めて返す。クライアントはトグルの状態に応じてどちらを表示するか選ぶだけで、追加リクエストは発生させない。

**理由**: モックで確定した「ゴースト線＝選んでいない側を薄く重ねて表示する」を実現するには、そもそも両方の値が同時にクライアントにある必要がある。トグルのたびに再フェッチする設計は、切替の体感速度を落とすうえ、既存の「予想はサーバが算出しクライアントは描画に徹する」原則とも相性が悪い（クライアント側で補間して両方作る誘惑が生まれる）。

**却下した代替案**: `basis` をクエリパラメータにしてトグルごとに再取得する設計。実装は単純だが、上記の理由で採用しない。

### 2. 「直近7日」は常に「今日を含む過去7日」。分母は常に7固定で、月をまたいで前月のデータも数える

分母（対象日数）は常に `7` で固定 SHALL。今日が月の1〜6日目でも「経過日数に縮めて割る」ような特別扱いはしない。対象期間（今日から遡る7日間）が前月にかかる場合は、前月末の `kakeibo_entry` も含めて7日ぶんの日々の出費を数える。

**理由**: ユーザー確定仕様（AskUserQuestionでの選択）は「今日から遡る7日間のローリング窓」であり、これは月の何日目であっても常に7日間そのもの。分母を経過日数に縮める特別扱いは、実装を複雑にするうえ「常に直近7日」というユーザー確定仕様と矛盾する（当初の設計メモで誤って混同していたので、ここで正す）。月をまたぐ取得さえ実装すれば、月初め数日目でもゼロ除算にはならない（前月に記録が無い＝トラッキング開始直後のような極端なケースでも、母数7・合計0円で1日平均0円になるだけで、算数としては破綻しない）。

**却下した代替案**: 経過日数が7日未満のときだけ分母を経過日数に縮める案。ユーザー確定仕様と食い違ううえ、「全体」と「直近7日」が月初だけ同値になるという分かりにくい特別扱いを生むため採用しない。

### 3. 週ごとの支出（分析タブ）は月境界をまたがない。月曜始まりの週バケットは「その月に属する日数分」だけ集計する

直近7日ベース予想の「ローリング窓」とは違い、週次棒グラフは月をまたいだ前月データを取得しない。月をまたぐ週（月初・月末）は日数が短い部分週としてそのまま表示する（例: 8月が土曜始まりなら第1週は8/1・8/2の2日分）。

**理由**: 週次棒グラフは「今月のふりかえり」という文脈（分析タブ）で、月次集計と同じ暦月スコープに揃えるのが素直。直近7日ベース予想は逆に「今この瞬間のペース」を知りたい指標なので月をまたぐ必要がある。同じ「週」という言葉でも目的が違うため、実装（データ取得範囲）も意図的に揃えない。

### 4. 折れ線グラフはSVGの手書きpathからCanvas＋Catmull-Romスプラインへ置き換える

`kakeibo-chart.js` の実績・予想の描画をCanvas 2D APIに変更し、同じ日次累計データをCatmull-Rom→ベジェ変換で滑らかに描く。値は変えず、描き方だけを変える。

**理由**: ユーザーから「折れ線がガタガタで好きじゃない」というフィードバックがあり、モックでCanvas＋スプラインに変更して合意済み。SVGの手書きpathで滑らかな曲線を表現すると制御点の手計算が大量に必要になり保守性が低い。

**トレードオフ**: Canvasは要素がDOMノードとして現れないため、既存/新規のe2eで「線の形」を直接アサートできない。代わりに、基準トグル操作の結果として変わる**テキスト**（月末予想額・1日平均・上限超過日）と、`<canvas>` の `aria-label`（サーバ値から組み立てる説明文）をアサート対象にする。

### 5. グラフ内テキストは「今日」「予想」「固定費・上限の軸ラベル」に絞り、予定出費額・交差日はグラフ外に出す

交差日はグラフ下のフッター文（既存の `kb-cross`）に1箇所、予定出費・特別費は折れ線直下の内訳行に1箇所、という「1情報1箇所」を徹底する。固定費額・上限額は軸のスケール感を示す薄いラベルとしてグラフ内に残す（カードヘッダー・内訳行の表示と重複してよい）。

**理由**: モックでグラフ内の文字被り（予定出費・交差日・着地額が重なって読めない）が指摘され、予定出費額・交差日はグラフ外に出す形で合意済み。ただし実装後の見た目調整（issue #105、2026-08-19）で、固定費額・上限額まで完全にグラフから除くと軸の目盛りが読めず不親切と判断し、この2つだけは薄いラベルとしてグラフ内に残すことにした（カードヘッダー・内訳行との重複は許容する）。

### 6. ホームの「無駄遣い」カードは、合計額・上限のゲージだけに絞る

ホームの「無駄遣い」カードから、変動費に占める割合（%）の数値表示と、「あと¥Xを抑えると月末の超過が¥Yに改善する」という文言を削除する。合計額と、上限に対するゲージ（超過していれば色で分かる）だけを残す。

**理由**: 実装後の見た目調整（issue #105、2026-08-19）で、数字が多いほど一覧性が落ちると判断した。上限を超えているかどうかはゲージの色と長さで十分に伝わり、割合や改善見込みの文言は無くても実用上困らない。予想の計算内訳・調整モーダル内の `.kb-effect`（特別費トグルの前後比較）は対象外で変更しない。

### 7. 内訳主行に「これまでの平均との差」の文字併記はしない。直近7日ゾーンは帯のまま、「定規」表現は不採用

折れ線直下の主行は選んでいる基準の1日平均だけを表示し、もう一方の基準との差分（例:「これまでの平均¥1,540より-¥780/日」）は文字で併記しない。差は既にグラフのゴースト線（薄い予想曲線）で視覚的に示されているため、文字での重複表現を省く。

直近7日ゾーンの視覚化は、実装過程で一度「予想の直線を今日で折り返して手前へ伸ばす定規」表現を試したが、グラフがごちゃつくため不採用にした。薄青の帯（当初案）は残し、直近7日ベースを選んでいるときに濃さを強める。

**理由**: 実装後の見た目調整（issue #105、2026-08-19）で、文字ラベル・定規の両方がグラフを読みにくくすると判断した。帯だけを残すことで、「直近7日を元にした」という情報自体は失わずに視覚要素を絞れる。

## Risks / Trade-offs

- [直近7日が月をまたぐと前月データの取得が必要になり、`kakeibo_entry` のクエリ範囲が「月キー単位」から「日付範囲単位」に変わる箇所が増える] → `forecastMonth` 内で直近7日用のクエリだけ `day_key BETWEEN` の日付範囲指定に変更し、月単位の既存クエリ（`listEntries(db, monthKey)`）はそのまま残す。既存の月次集計・特別費判定のロジックには触れない。
- [Canvas化でe2eの検証手段が減る] → 上記Decision 4のとおりテキスト・aria-labelをアサート対象にする。既存のSVGベースe2eがあれば、この変更で影響を受ける箇所を洗い出して更新する。
- [週次棒グラフと直近7日予想が「週」という同じ言葉で違う区切り方をするため、実装者が混同して同じ関数を使い回すリスク] → design上で明確に別関数（`weeklyBreakdown`＝月境界内固定、`forecastMonth`の直近7日算出＝ローリング）に分け、コメントで区別を明記する。

## Migration Plan

スキーマ変更・データ移行は無し。既存の `forecastMonth` / 分析APIのレスポンス形状が拡張されるのみ（フィールド追加）。ロールバックは変更のrevertのみで完結する。
