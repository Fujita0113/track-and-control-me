## Context

長期目標を一時的に止める手段がなく、いまは「ルールを理由つきで削除 → 期間後に作り直す」しかない。作り直すとルールの安定キー（`rule:<id>`）が変わるため沿革とレポート①の行が分断され、30日チャレンジも走り切れない（issue #60）。

既存の骨格のうち、この変更が乗る場所は3つある。

- `listActiveRules(db, dayKey)` が当日の実効ルールを決め、`evaluateDay` が全ルール AND で解錠を判定する。**ルールは必ずどこかの目標に属する**（`createRule` の呼び出しは `addRuleToGoal` のみ）ため、目標単位の凍結はゲート除外として素直に表現できる。
- レポート①には既に `inactive`（対象外）の概念があり、達成日数は「その日ゲートにあったルールが1つ以上あり、全部 met」で数える。**全ルールが対象外の日は達成にも未達成にも数えられない**ので、凍結日はこの枠にそのまま乗る。
- `end_day` は既に前方向にのみ伸びる（`goal-lifecycle-fork` の「伸ばす」）。凍結ぶんの延長は新概念ではなく、その2つ目の理由になる。

制約として、**日次 cron を使ってはならない**（`goal-check-gate`: 完全ローカル・オンデマンド起動でも正しく発火させるため、状態は対象日から遅延導出する）。凍結の発効・自動解凍・月枠の回復はすべて日付からの導出で表現する必要がある。

## Goals / Non-Goals

**Goals:**
- 目標単位の一時凍結を、既存の「状態は保存せず day_key から導出する」流儀のまま実装する
- 凍結日を「無かった日」として扱い、期限・カレンダー・達成日数の3つで一貫させる
- 凍結を逃げ道にしない制約（翌日発効・アプリ全体で月1回・全操作を沿革に記録）を仕様として実装する
- 既存の `GoalStatus`（upcoming/active/completed）と、それを読む UI・レポート・完走フォークを壊さない

**Non-Goals:**
- ルール単位の凍結（凍結は目標単位。個別ルールを止めたいなら理由つき削除が既にある）
- 凍結期間の短縮（早く戻りたい場合は解除。`end_day` を前へ動かす手段は作らない）
- 凍結の予約を複数積むこと（1目標1件・延長で代替する）
- 凍結回数の上限を月枠以外に足すこと（延長は無制限）

## Decisions

### D1. 凍結は「日区間」でモデル化し、新しい status を作らない

`goal_freeze(goal_id, start_day, end_day, reason, created_at, updated_at)` を追加し、凍結の状態は保存せず対象日から導出する（`today < start_day`＝予約中／`start_day <= today <= end_day`＝凍結中／それ以降＝解凍済み）。

**`GoalStatus` に `frozen` を足さない。** 凍結中も `status` は `active` のままにする。理由は2つある。

1. `status === 'active'` で絞っている消費側（`reflection.js` の `activeGoals`、レポート、完走フォーク）が無傷で済む。とくに振り返りタブのカードが消えると**凍結解除の導線に辿り着けなくなる**（`goal-freeze` の「カードを消してはならない」はこの事故の予防）。
2. D2 の延長規則により、凍結中は実効 `end_day` も毎日 1 日ずつ伸びる。したがって `today > end_day` に到達せず、**完走判定に特別扱いを足さなくても凍結中は完走しない**。

代替案として「凍結中を新 status にして `deriveStatus` の先頭で短絡する」を検討したが、status を読む全箇所に分岐が波及するわりに、得られるのは表示の都合だけだった。凍結中であることは `GoalView.freeze` で表現する。

### D2. 実効 `end_day` は純関数で導出し、DB 列は書き換えない

```
frozenDaysUpTo(goal, today) = Σ 各凍結区間 [start_day, min(end_day, today)] の日数（負は 0）
effectiveEndDay(goal, today) = addDaysKey(goal.end_day, frozenDaysUpTo(goal, today))
```

`goal.end_day` 列は「凍結を除いた素の終了日」のまま据え置き、読み手が都度この純関数を通す。

代替案は「解除時に `UPDATE goal SET end_day = ...` で焼き込む（materialize）」だったが、採らない。焼き込みだと**凍結中に日付が元の `end_day` を越えた瞬間、解除前に完走してしまう**ため、結局 `deriveStatus` に凍結の特別扱いが要る。lazy write-on-read（読むたびに差分を書き足す）も検討したが、冪等性のために `accounted_through_day` のような可変状態が増え、テストが書きにくい。純関数なら入力（凍結区間・today）から出力が決まり、`day-key.ts` の既存ヘルパの上に vitest で直接検証できる。

代償として、`goal.end_day` を直接読む箇所を全部通し替える必要がある（`toGoalView` の `dayCount`/`dayNumber`、`deriveStatus`、`getGoalReport` の `dayCount`/`elapsedDays`/`dayKeys`、`addRuleToGoal` の延長判定）。**漏れると凍結が効いていない箇所ができる**ので、洗い出しはタスクに明示し、`goal.end_day` の直参照が残っていないことをレビュー観点にする。

### D3. ゲート除外は `listActiveRules` の1箇所に置く

「その日凍結中の目標に紐づくルール」を `listActiveRules` から除く。除外条件は**紐づく目標がすべて凍結中のときのみ**（`goal_rule` は M:N のため）。いま全ルールは1目標にしか紐づかないが、条件を最初から M:N で正しく書いておく。

`evaluateDay` には触らない。`hasRuleSet`／`conditionsMet` の「ルール0なら達成不能」もそのまま残す（D8）。これにより、凍結が解錠の裏口にならないことが**評価器を変えないこと**によって保証される。

`listDueRules`（今日タブのトースト）も同じ除外を通す。ここを別経路にすると「凍結したのに写真ルールの通知だけ来る」が起きるため、除外は共通のヘルパ（`frozenGoalIdsOn(db, dayKey)`）に集約する。

### D4. 月枠は行の存在から導出する（cron なし）。事実は別の追記専用ログに残す

月枠の判定は「その月に `start_day` を持つ `goal_freeze` 行が存在するか」だけで済ませる。

- 予約中の行も存在するので**枠を占有**する。
- **発効前の取消は行の削除**なので、枠は自動的に戻る。
- **発効後は行が残り続ける**ので、解除しても枠は戻らない（解除は `end_day` の切り詰めであって削除ではない）。0日凍結（発効当日に解除）でも行は残るため、予約→発効→即解除→再予約の抜け道が塞がる。

消費フラグや月次リセットのような可変状態も cron も要らず、`start_day` の `YYYY-MM` を見るだけで決まる。取消と解除を**別操作**（行削除 / `end_day` 切り詰め）に分けたのは、この導出を成立させるためでもある。

ただし取消で行を消すと、沿革が要求する「取り消した予約も消してはならない」を満たせなくなる。そこで**現在の状態を持つ行**と**起きた事実のログ**を分ける（`rule` と `rule_change` の関係と同じ構造）。

- `goal_freeze`: 生きている凍結（予約中／凍結中／解凍済み）。取消で削除される。
- `goal_freeze_change`: 追記専用ログ（`goal_id`・`day_key`・`op`（`reserve`/`cancel`/`extend`/`release`）・`start_day`・`before_end_day`・`after_end_day`・`reason`・`created_at`）。**`goal_freeze` へ FK を張らず `goal_id` を持つ**ので、行が消えてもログは残る。

沿革はこのログだけを読む。可変状態（`goal_freeze`）と履歴（`goal_freeze_change`）が分かれるので、取消が枠を返すことと、取消の事実が残ることが両立する。

### D5. 翌日発効と即日解除の非対称を仕様として持つ

凍結の開始は翌日発効（`start_day` = 予約日の翌日で固定。API はクライアントから `startDay` を受け取らない）、解除は即日発効（`end_day` = 解除日の前日）。

非対称の理由は「緩める操作には摩擦を、締める操作には摩擦を足さない」という既存の思想（理由必須が全ルール操作にかかる一方、達成には理由が要らないのと同じ）。凍結中の当日を解除でゲートに戻すのは、その日の評価を厳しくする方向なので即時でよい。過去日の `unlock_evaluation` は `is_final` で保護されており、いずれの操作も過去を書き換えない。

### D6. 沿革は `entries` を壊さず `freezes` を並べて足し、並び順はサーバが決める

`Chronicle` に `freezes: FreezeEntry[]` を追加する。`ChronicleEntry` を union 化する案は、既存の形（`ruleId`/`target`/`label`/`change`/`answers`）を前提にした contract と描画側が全面改修になるため採らない。凍結イベントを `rule_change` 行として書く案も、ルールの操作履歴を汚し「凍結はルール操作ではない」という事実に反するので採らない。

ただし spec は「ルール操作と同じ時系列に、決定的な並びで」を要求するので、マージ順序を UI の実装詳細にしない。`entries` と `freezes` の両方に **`sortKey`（`dayKey` → `createdAt` → `id` の三段）** を持たせ、サーバ側でその値を確定させる。UI は連結して `sortKey` で安定ソートするだけになり、並びの決定性はサーバの vitest で検証できる。

`FreezeEntry` は `kind: 'reserve' | 'cancel' | 'activate' | 'extend' | 'release'` を持つ。`reserve`/`cancel`/`extend`/`release` は `goal_freeze_change`（D4）をそのまま読む。`activate`（発効）だけはログに書かず、生きている `goal_freeze` の `start_day` が `untilDayKey` に到達しているかから**導出して合成**する（cron が無いので「発効した瞬間に書く」ことができない。D1 と同じ理由）。取り消された予約は行が消えているため `activate` を合成せず、ログの `reserve`/`cancel` だけが残る。

### D7. レポートは `frozen` を `inactive` と別のフィールドにする

`ReportDayCell` に `frozen: boolean` を足す。`inactive`（開始前・削除後）と同じフラグに畳まない。同じ灰色にしてしまうと、あとから自分のレポートを読んだときに「まだ始めていなかった日」「ルールを消した日」「凍結した日」の区別がつかず、沿革と突き合わせないと読めなくなる。

集計側は `wasActiveOn(rule, dayKey)` に凍結条件を足すだけで、達成日数のロジック（`applicable.length > 0 && applicable.every(met)`）は変えない。凍結日は全ルールが対象外になるので `applicable.length === 0` となり、自動的に分子にも分母にも入らない。

### D8. 有効ルール 0 の日は評価を変えず、今日タブの文言だけ変える

`conditionsMet = perCondition.length > 0 && ...` はそのまま。今日タブの `${date} のルール未設定 (達成不能)` を、振り返りタブでルール／目標を作れば当日から解錠できる旨の案内に差し替える。今日タブに作成 UI は置かない（`editable-rule-registry` の「今日タブにできるのは回答のみ」を維持）。新しく作ったルールは `start_day` が当日なのでその日から合流し、詰みにはならない。

### D9. API は取消と解除を分ける

| メソッド | パス | 用途 |
|---|---|---|
| POST | `/api/goals/:id/freeze` | 予約（`endDay`・`reason`。`startDay` は受け取らず翌日固定） |
| PATCH | `/api/goals/:id/freeze` | 期間変更・延長（`endDay`・`reason` 必須。発効後は後ろへのみ） |
| DELETE | `/api/goals/:id/freeze` | 取消（発効前のみ。発効後は 409） |
| POST | `/api/goals/:id/freeze/release` | 解除（凍結中のみ。発効前は 409） |
| GET | `/api/goals/freeze/quota` | 今月の枠の状態（使用済みか・使った目標名と期間・回復する月） |

`PATCH` は発効前後を問わず理由必須にする（発効前の短縮も沿革に残す）。枠の状態を目標一覧に重複して載せず独立エンドポイントにしたのは、枠がアプリ全体で1つだからである。

### D10. デモモードに凍結サンプルを焼き込む

プロジェクトルールにより、日数が絡む機能はデモモードで成果を再現する。`demo-seed.ts` の固定 day_key サンプルに凍結を1件足し、`POST /api/demo/reset` → `GET /api/demo/goals/:id/report` で「凍結マス・延長された `Day N/M`・沿革の凍結エントリ」が出るところまで通す。

既存の筋書き（達成 24/30・中盤の谷）を壊さないよう、**凍結は既存の谷日に重ねる**。凍結日は達成日数の分母から抜けるため、谷に重ねれば「未達成だった日が凍結の対象外になる」形になり、達成日数の期待値は変わらないか増える方向にしか動かない。`demo.test.ts` の期待値（実践数・達成日数）は実測に合わせて更新する。

### D11. 一時凍結 UI は専用モーダルダイアログ形式とし、複数選択・ルール表示に対応する

目標ごとにカード内で独立して入力させるのではなく、振り返りタブの導線から「一時凍結モーダル」を起動する。
モーダル内の入力・選択順序および仕様は以下の通りとする：
1. **凍結理由**と**凍結期限 (end_day)** を入力（理由必須・期限指定）
2. 凍結対象となる**長期目標を複数選択**（チェックボックスで複数選択可能）。各目標項目には目標名だけでなく、紐づくルール一覧を**箇条書き形式**で、アイコンおよび数値条件・閾値（例: 「総作業時間 240分以上」などの何分以上かという詳細表現）を含めて表示し、ユーザーが止めたいルールから対象目標を直感的に判別できるようにする。
3. 「一時凍結する」ボタンで決定（選択された全目標を一括で予約）

同一理由・同一期限で複数の目標を選択して一気に決定できるため、操作の摩擦を減らし、理由・期限の必須性や枠の状態を視認しやすくする。1回の凍結機会において選択された複数目標の一括予約を許可する。


## Risks / Trade-offs

- **実効 `end_day` の通し替え漏れ** → 凍結が一部の画面でだけ効いていない状態になる。`goal.end_day` の直参照箇所（`deriveStatus`・`toGoalView`・`getGoalReport`・`addRuleToGoal`）をタスクに列挙し、純関数1本に集約する。凍結中に完走判定が走らないことを vitest で直接検証する。
- **月枠がアプリ全体で1つ** → 無関係な2つの目標が同じ月に事情を抱えると片方が凍結できない。issue の意図（逃げ道にしない）を優先した意図的な制約。UI で「誰がいつ枠を使ったか・いつ回復するか」を全カードに出して、詰まりの理由が読めるようにする（`goal-freeze` の要件）。
- **延長が無制限＝実質の永久凍結** → 翌日発効により当夜の解錠には使えないため、逃げ道としての価値は低い。抑止は理由必須と沿革への蓄積に委ねる（「7/20 凍結 → 7/27 延長 → 8/3 延長…」が並ぶこと自体が抑止になる）。回数上限は入れない。
- **凍結中に評価行が作られない日がある** → レポート①は `frozen` で描くため `unlock_evaluation` を引かず、欠測＝未達成の扱いに落ちない。凍結日のセルは評価行の有無に依存しないことをテストで固定する。
- **凍結と「未決着の単発ルールで完走保留」の相互作用** → `unresolvedSingleRules` は凍結中もそのまま効き、完走をさらに遅らせうる。どちらも「進行中に留める」方向なので矛盾はしないが、テストで両方が同時に効く状況を1本置く。

## Migration Plan

1. `migrations.ts` に `goal_freeze` を追加（新規テーブルのみ・既存テーブルの ALTER なし・`goal_id` は `ON DELETE CASCADE`）。既存 DB は空の新テーブルが増えるだけで、凍結が1件も無い状態は `frozenDaysUpTo = 0` となり、全導出が現在の値と一致する（無変更で後方互換）。
2. 純関数（`frozenDaysUpTo` / `effectiveEndDay` / `frozenGoalIdsOn` / 月枠）→ サービス → API → UI の順で入れる。1 の直後の時点で既存テストが全て緑のままであることを確認する。
3. デモシードと `demo.test.ts` の期待値更新は、レポート側（D7）が入ったあとに行う。
4. ロールバック: `goal_freeze` に行が無ければ挙動は変更前と同一なので、UI の導線を落とすだけで実質無効化できる。

## Open Questions

- 沿革の凍結エントリの見た目（アイコン・ルール操作との視覚的な差）と、レポート①の凍結マスの表現（斜線か別色か）は、既存の描画コードに合わせて実装時に決める。
- 凍結中の目標カードで、畳んだルールブロックをユーザーが展開して**読める**ようにするか（操作はさせない）は実装時の裁量とする。
