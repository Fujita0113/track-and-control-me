## Context

現状の2つのボタンは「制限のある弱い方（凍結）」と「制限のない強い方（終了）」で、強い方がいつでも押せる。

| | 発効 | 上限 | 期限 | ゲート離脱の実装 |
|---|---|---|---|---|
| 一時凍結 | 翌日固定 | アプリ全体で月1回 | 凍結日数ぶん前へ延長 | `frozenGoalIdsOn` による**導出**（`rule` 行は触らない） |
| 終える | 当日 | なし | — | `removeRule` で `status='removed'`（**破壊的**） |

凍結が今夜に届かないため、今夜ノルマを外す正当な用事（明日の面接の課題）が終了ボタンへ流れ込む。`goal-lifecycle-fork` は「抑止は記録が担う／発効を遅らせる仕掛けで塞いではならない」と明文化しているが、この抑止は**まだ調子が良いときにしか効かない**（記録の汚れを気にしなくなる局面が、ブレーキの必要な局面と一致する）。

既存の設計方針で守るもの:
- **日次 cron を持たない**。状態は保存せず、`day_key` と行から都度導出する（`goal-check-gate` / `goal-freeze` D1）。
- 過去の判定を書き換えない（`unlock_evaluation` は確定済み）。
- 月枠は**発効日（`start_day`）の属する月**で数える（`quotaMonthOf`）。

## Goals / Non-Goals

**Goals:**
- 今夜ノルマを外す正当な手段を、**上限つきで**提供する（当日凍結）。
- 終了から当日破壊の力を取り上げ、「本を閉じる」操作に戻す。
- 終了が翌日発効になることで生じる不可逆な待ち状態に、取消を用意する。
- 抑止の根拠を「記録の汚れ（性善説）」から「月1枠（機械的制限）」へ移す。

**Non-Goals:**
- ルール単体の削除の発効タイミング（`editable-rule-registry`「当日から効く」）は変えない。→ 既知の穴として proposal に明記済み。
- 沿革の見た目の改修（issue #88 で別建て）。
- 月枠の回数チューニング。まず月1回で運用し、足りなければ後で増やす。
- 当日凍結を過去日へ遡って打つこと（当日のみ。過去は書き換えない）。

## Decisions

### D1: 凍結に種別カラムを足し、`period` / `same_day` の2モードにする

`goal_freeze` に `kind TEXT NOT NULL DEFAULT 'period'` を追加する（migration version 27）。既存行はすべて `period` になる。

- `period`（従来）: `start_day = today + 1`・`end_day` 任意・延長可・**期限を延ばす**。
- `same_day`（新）: `start_day = end_day = today` 固定・延長不可・**期限を延ばさない**。

**なぜ列を足すか**: 「期限を延ばすか」は `start_day` から導出できない（`start_day = today` は当日凍結の印だが、翌日になれば `start_day < today` の凍結中区間と区別がつかなくなる）。事実として保存する必要がある。

**代替案**: 別テーブル `goal_same_day_freeze`。却下 — ゲート離脱・月枠・沿革の3経路すべてで区間として同じ扱いをするので、テーブルを分けると3か所で UNION することになる。

### D2: 「期限を延ばさない」は `effectiveEndDay` の入力から `same_day` を除くことで表す

`FreezeInterval` に `kind` を持たせ、2つの用途で母集団を変える:

| 用途 | 対象 | 理由 |
|---|---|---|
| `effectiveEndDay`（実効 `end_day`） | `kind='period'` のみ | 当日凍結は期限を延ばさない（等価交換の代金） |
| `frozenGoalIdsOn`（ゲート離脱） | 全区間 | 今日のノルマは外れる（当日凍結の目的そのもの） |
| `frozenDayKeySet` / `frozenDaysUpTo`（ペースの分母） | 全区間 | 対象外の日なので分母から抜ける |
| レポート①のセル `frozen` | 全区間 | 対象外として表示（既存の見た目のまま） |

`goalFreezeIntervals` は `kind` つきで返し、`effectiveEndDay` は内部で `kind !== 'same_day'` を絞る。**`frozenDaysUpTo` の呼び出し側で絞らない**（`goalPace` の `elapsedDays = totalDays - frozen` は全凍結日を引く必要があるため。ここを間違えると当日凍結の日が分母に残り、平均が下がる）。

帰結: 当日凍結した日は `Day N/M` の M が伸びず N だけ進むので、**残り日数が1日減る**。これが「夜は取れるが 30 日は伸びない」の実体。

### D3: 当日凍結は延長できない

`updateFreeze`（`op='extend'`）を `kind='same_day'` の行に対して拒否する。許すと「当日凍結 → 翌日まで延長」で、当日発効の凍結が期限延長つきの期間凍結に化ける（月枠1回で当日破壊と期限延長の両取り）。

**解除は許す**。`releaseFreeze` は `end_day` を前日へ切り詰めるだけで、当日凍結なら `end_day = today - 1 < start_day` となり凍結日数0になる。既に「発効当日の解除は凍結日数0日」という前例があり（`goal-freeze`）、ゲートを厳しくする方向の操作なので摩擦を足す理由がない。**月枠は戻らない**（既存規則どおり。発効した凍結は枠を解放しない）。

### D4: 月枠は「発効日の属する月」の規則をそのまま一般化する

既存 `quotaMonthOf(today) = (today+1) の月` は「予約は翌日発効」という前提の**特殊化**だった。一般形は **`start_day` の属する月**で、これは既に `quotaRowForMonth` の実装（`substr(gf.start_day,1,7)`）と一致している。

- 当日凍結の枠 = `today` の月
- 期間凍結の枠 = `today + 1` の月

月の最終日だけこの2つが食い違う。`GET /api/goals/freeze/quota` のレスポンスを `{ ...期間凍結の枠（既存の形のまま）, sameDay: 当日凍結の枠 }` に拡張し、モーダルが選択中のモードに応じて表示する。**両モードは同じ1枠を奪い合う**（同じ月なら片方を使えばもう片方も塞がる）。

**代替案**: 当日凍結を別枠にする。却下 — ユーザーの合意は「月1回の枠を消費」。分けると当日枠だけ毎月余って、当日凍結が期間凍結より安い選択肢になり、逆の歪みが生まれる。

### D5: 終了は `ended_day_key = today + 1` を書くだけ。ルール行は触らない

`deriveStatus` は既に `today >= goal.ended_day_key` で判定しているため、`ended_day_key` に翌日を入れると**今日は自動的に進行中のまま**になる（コード変更不要）。

ゲート離脱は凍結と同じ導出方式にする:

```
endedGoalIdsOn(db, dayKey) = SELECT id FROM goal WHERE ended_day_key IS NOT NULL AND ended_day_key <= dayKey
```

`listActiveRules(db, dayKey)` の既存フィルタ `isFullyFrozen`（紐づく全目標が凍結中ならそのルールを落とす）を `isFullyInactive`（全目標が**凍結中または終了済み**なら落とす）へ一般化する。`listActiveRules` はゲート（`rules/evaluate.ts`）と今日タブ（`listDueRules`）の唯一の入口なので、ここ1か所で足りる。

**なぜ `removeRule` をやめるか**（3つとも独立に決定的）:
1. **取消が実装できない**。`removeRule` は `status='removed'` にして沿革へ `op='remove'` を追記する破壊的操作で、rule-registry に「取り消す」操作は無い。終了予約を取り消すには、消したルールを全部戻して沿革の行も消す必要があり、追記専用ログの原則に反する。導出方式なら取消は `ended_day_key = NULL` の1フィールド更新。
2. **既存方針との一貫性**。凍結は `rule` 行を触らずに導出でゲートから外している。終了は「永続の凍結」と同じ形になる。
3. **cron が要らない**。翌日に実際の削除処理を走らせる仕掛けが不要。

**副作用（受け入れる）**: 終了時に⑤沿革へルール1件ごとの「−削除（理由）」が生えなくなる。終了の記録は大きい沿革の「−終える」1件と⑤沿革の最終エントリ（`chronicleEndedNote`）が担う。ルール数ぶん同じ理由が並ぶ行は元々ノイズであり、失って困る情報は無い。**過去に終了済みの目標のルール（既に `status='removed'`）はそのまま**にする（過去を書き換えない）。

**副作用（要確認）**: 終了済み目標に紐づくルール行が `status='active'` のまま残る。`listActiveRules` 以外に `status='active'` を全件走査する経路が無いことは確認済み（`rule-registry.ts:364` の1本のみ）が、目標ごとの一覧（`linkedRules`）を使う画面が終了済み目標を描画しないことを実装時に確認する。

### D6: 完走フォークの「終える」も翌日発効（発効タイミングを分けない）

既存 `goal-lifecycle-fork` の MUST NOT「進行中の終了と完走フォークの終えるで発効タイミングを分けてはならない」を**維持**する。

当初「完走後は当日でよい（壊すべき今日のノルマが無い）」と考えたが**誤り**: 完走した目標の永続ルール（`end_day = null`）は `isRuleActiveOn` で常に有効なので、「続ける／終える」を答えるまで**ゲートに残り続ける**。完走後の終了も当日のノルマを破壊できてしまうため、同じ問題が同じ形で起きる。

### D7: 終了予約の取消は発効前のみ

`today < ended_day_key` のときだけ `ended_day_key`・`end_reason`・`outcome_met`・`final_pace_json`・`lifecycle_*` を NULL に戻す。発効後（`today >= ended_day_key`）は拒否する（凍結の「発効後は取消できません」と同じ形）。

**終了時に取り消した凍結予約は復元しない**。`endGoal` は未発効の凍結予約を `cancelFreeze` するが、これは月枠を解放する破壊的操作で、取消時に元へ戻すと「予約 → 終了 → 取消」で枠の状態が復元される必要があり、その間に他の目標が枠を取っていたら復元できない。取消しても凍結予約は戻らないことを UI の確認文言に書く。

**証拠写真は消さない**。終了時に保存した画像は `goal_journal_image` に日記画像として入っている。取り消しても画像は残す（記録は消さない既存原則）。

### D8: `final_pace_json` は終了を**申し込んだ時点**で焼き込む

翌日発効だが、ペースの焼き込みは今日行う。翌日に走るコードが無いため。差は最大1日ぶんで、意味としては「終えると決めた時点のペース」。取消したら NULL に戻る（D7）。

**代替案**: 発効日以降の初回読み出しで遅延焼き込み。却下 — 読み出しに隠れた書き込みを持ち込むのは既存方針（導出のみ）に反する。

### D9: 派生状態「終了予約中」は保存しない

`GoalView` に `endingOn: string | null`（= 発効前の `ended_day_key`）を足し、UI 側で「終了予約中（明日から）」＋取消ボタンを出す。状態そのものは `status='active'` のままで、`goal-challenge` の派生規則（`today >= ended_day_key` で「終了」）は変えない。

### D10: 一時凍結モーダルの既定は期間凍結（当日凍結は明示的に選ぶ）

種別セレクタの初期値は**期間凍結（翌日発効）**にする。当日凍結を既定にすると、今夜のノルマを壊すまでのクリック数が最短になり、衝動に対する摩擦が消える。当日凍結は「わざわざ選ぶもの」であるべき。副次的に、既存の `e2e/goal-freeze-reserve-flow.spec.ts`（期間凍結の予約フロー）が無改変で通り続ける。

### D11: 終了まわりの文言と導線（既存 e2e が凍結しているため propose で確定させる）

| 箇所 | 変更前 | 変更後 |
|---|---|---|
| 終了成功トースト | `目標を終えました` | `明日からこの目標を終えます` |
| 目標カードのバッジ | 発効前も `終了` | 発効前は `進行中` のまま ＋ `終了予約中` バッジ（発効日を併記） |
| 削除ボタンの表示条件 | `status !== 'ended'` | `ended_day_key == null`（終了予約中も隠す。サーバの削除ガードと一致させる） |
| 「終える」ボタン | 終了済みには出さない | 終了予約中にも出さない。代わりに「終了を取り消す」を出す |

大きい沿革の「−終える」行は**発効前から並ぶ**（`ended_day_key` 由来・取消で消える）。発効前の行には `予約中` の語と発効日を添える。当日にしか走れない e2e が終了の行を検証できなくなるのを避けるためでもあるが、根拠は⑤沿革が既に「凍結を予約」を1エントリとして記録している前例に揃えること。

**代替案A（`ended_day_key = today` のままゲート離脱だけ翌日にする）**: 却下 — 「終了」と表示しながら今夜のゲートにルールが残る状態になり、レポート・ペース・削除ガードの各所で「終わっているのに動いている」矛盾を抱える。表示だけ先に嘘をつく設計は後で必ず破綻する。

**代替案B（発効するまで大きい沿革に載せない）**: 却下 — 沿革の「終える」行を当日に検証できなくなり、`e2e/goal-target-hours.spec.ts` が背骨として踏んでいる筋（作成→終える→沿革に3つ並ぶ）が1日では通せなくなる。予約中の印をつけて載せれば事実として正確でもある。

## Risks / Trade-offs

- **[当日凍結が「今夜の逃げ」に使われる]** → 月1枠という機械的上限が唯一かつ十分な抑止。理由必須で沿革にも残る。枠が足りないと感じたら回数を増やす（Non-Goal に置いた運用判断）。
- **[月1枠を当日凍結で使い切ると、本来の期間凍結（出張・帰省）が打てなくなる]** → 意図した設計。当日凍結は「今日1日と引き換えに月の枠を丸ごと使う」高い買い物で、それが衝動的な使用への値付けになる。運用してみて痛ければ回数を増やす。
- **[ルール単体削除で今夜のノルマを消せる穴が残る]** → 塞がない（proposal の「既知の穴」）。理由必須＋沿革＋作り直しの労力が摩擦。塞ぐと編集モデル全体（`editable-rule-registry`）を壊す。
- **[`status='removed'` をやめたことで、終了済み目標のルールがどこかの一覧に漏れる]** → `listActiveRules` が唯一の全件走査経路であることは確認済み。実装時に目標ごとの一覧（振り返りタブ・目標カード）が終了済み目標を描画しないことを確認するタスクを置く。
- **[月末の枠表示が2つの月にまたがって分かりにくい]** → モーダルで選択中のモードに対応する枠だけを表示する。既存 spec の「表示側と重複チェックが食い違ってはならない」要求を、モードごとに満たす。
- **[終了予約中の目標を削除できない]** → 既存の削除ガード（`ended_day_key != null` で拒否・issue #86）がそのまま効く。取り消せば削除可能に戻るので詰まらない。

## Migration Plan

1. migration version 27: `ALTER TABLE goal_freeze ADD COLUMN kind TEXT NOT NULL DEFAULT 'period'`。既存行は `period` になり、実効 `end_day` もペースも従来どおり。
2. `goal` テーブルは変更なし。既存の終了済み目標は `ended_day_key` が過去日なので `today >= ended_day_key` で「終了」のまま。
3. ロールバック: `kind` 列は無視されても `period` 相当の動作になるため、サーバを戻せば当日凍結行が「その日1日の期間凍結」として扱われる（期限が1日延びるだけ）。破壊的な不整合は起きない。

## Open Questions

- 月1枠で足りるかは運用で見る。足りなければ「当日凍結だけ月2回」のような別枠化を後から入れる（D4 の代替案として検討済み）。
