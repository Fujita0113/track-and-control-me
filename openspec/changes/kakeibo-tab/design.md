## Context

`ref/kakeibo/kakeibo-mock.html`（5巡目・スクショ10枚・`ref/kakeibo/design-notes.md`）が仕様である。モックの数字は**全画面で辻褄が合っている**（下の「数字の筋書き」で検算済み）。したがってモックの数値そのものを凍結テストの期待値に使える。

**4巡目からの方針転換**: 当初は「その買い物が何日もったか」を聞いて名称ごとに日単価を持つモデルだった。issue #94 のコメント（「複雑なロジック組みすぎた」）でこれは取り下げられ、予想は **今月の出費 ÷ 経過日数 × 月の日数** の一本になった。捨てたのは予定日数・実績日数・記録時の1問・3状態・名称ごとの基準4択・カバー期間の帯・日数の一括編集・カテゴリ月枠。残る調整弁は**特別費**（この出費は毎月は起きないので平均に混ぜない）だけである。

分かっている足場:

- **家計簿は既存データに一切依存しない**。`session` / `task` / `goal` / `rule` のどれとも結合しない。だから新規テーブルだけで完結し、家計簿を使わないユーザーの挙動は現状と**完全に同じ**になる。
- **解錠ゲートは既に「シグナル」の受け口を持っている**。`PLANNING_SIGNAL_KEYS`（`planning.ts`）が中央レジストリで、`resolvePlanningSignal` の `switch` に1本足せば、ルールの作成・編集・沿革・latch・今日タブの表示が**全部既存経路に乗る**（`kanban-rule-conditions` D1/D2 のパターン）。新しい `RuleTarget` を作る必要は無い。
- **画像の縮小・再エンコードは既にある**。`static/js/images.js` の `shrinkImage()` が長辺1600・JPEG q0.85 に落として data URL を返す。レシートはこれをそのまま使う。ただし保存先の `goal_journal_image` は `goal_id NOT NULL` なので**再利用できない**（D12）。
- **月の区切りは day_key で足りる**。`day_key` は既に作業日境界（04:00）を織り込んだ 'YYYY-MM-DD' なので、`substr(day_key, 1, 7)` がそのまま「1日〜末日」の月になる（#94 の「月単位：1日〜末日」）。深夜2時のコンビニは前日の家計簿に入る＝作業日の感覚と一致する。
- **タブは6本になる**。`main.js` の数字キーは `Math.min(9, tabs.length)` で上限を取っているので、タブを足すだけで `6` が効く。

## Goals / Non-Goals

**Goals:**

- **予想を1本の式で出し、その式を隠さないこと**。画面に出ている1日平均と月末予想が算数として一致する
- **特別費で外した額を実績には残す**。除外していることを画面に出す（黙って推測しない）
- 単純按分が**月前半に上振れする**ことを演出で覆い隠さない
- 既存データ・既存挙動をゼロ改変で通す。新規テーブルだけ、既存テーブルへの `ALTER` を1つも出さない
- モックの数字を**そのまま**再現する（丸め規則まで含めて一意に決める）

**Non-Goals:**

- LLM との振り返り（#94 が明示的に後回し）
- 収入・資産・口座残高・複数通貨・銀行連携
- レシートの OCR・自動読み取り（画像は「後から見返す証拠」であって入力源ではない）
- 内訳の構造化・解釈（自由記述のまま。パースして品目集計などはしない）
- 家計簿を目標（`goal`）やルールの `TIMELINE` / `GROUP` 条件に結合すること（ゲートに出るのは「記録したか」の1点だけ）
- **日数の在庫と名称ごとの日単価**（issue コメントで取り下げ）
- 予想の高度化（移動平均・季節性・機械学習。単純按分を超えない）

## Decisions

### D1. 新規テーブル6本だけ。既存テーブルへの `ALTER` はゼロ

```sql
-- 支出レコード（台帳の実体）
CREATE TABLE kakeibo_entry (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  day_key TEXT NOT NULL,                 -- 買った日（作業日）
  name TEXT NOT NULL,                    -- 名称。まとめ登録は '' （D9）
  amount_yen INTEGER NOT NULL,           -- 整数円（D13）
  category TEXT NOT NULL,                -- FOOD|DAILY|FUN|SUDDEN|NONE
  importance TEXT,                       -- MUST|SEMI|WASTE / NULL = 内訳未入力（D9）
  is_special INTEGER NOT NULL DEFAULT 0, -- 1 = 手で特別費にした（D3）
  detail TEXT,                           -- 内訳の自由記述。NULL = 未入力（D10）
  bulk_from TEXT, bulk_to TEXT,          -- 非 NULL = まとめ登録（D9）
  receipt_id INTEGER REFERENCES kakeibo_receipt(id) ON DELETE SET NULL,
  created_at INTEGER NOT NULL, updated_at INTEGER NOT NULL
);
CREATE INDEX idx_kakeibo_entry_day ON kakeibo_entry(day_key);
CREATE INDEX idx_kakeibo_entry_name ON kakeibo_entry(name, day_key);

CREATE TABLE kakeibo_receipt (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  mime TEXT NOT NULL, bytes BLOB NOT NULL,
  width INTEGER, height INTEGER, created_at INTEGER NOT NULL
);

CREATE TABLE kakeibo_zero_day (day_key TEXT PRIMARY KEY, created_at INTEGER NOT NULL);

CREATE TABLE kakeibo_budget (
  month_key TEXT PRIMARY KEY,            -- 'YYYY-MM'
  cap_yen INTEGER NOT NULL, waste_cap_yen INTEGER NOT NULL,
  updated_at INTEGER NOT NULL
);

CREATE TABLE kakeibo_fixed_cost (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  month_key TEXT NOT NULL, name TEXT NOT NULL, amount_yen INTEGER NOT NULL,
  sort_order INTEGER NOT NULL DEFAULT 0,
  UNIQUE (month_key, name)
);

CREATE TABLE kakeibo_planned_expense (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  name TEXT NOT NULL, category TEXT NOT NULL,
  cycle_days INTEGER NOT NULL, next_day_key TEXT NOT NULL,
  amount_yen INTEGER NOT NULL,           -- 目安（D8）
  sort_order INTEGER NOT NULL DEFAULT 0, created_at INTEGER NOT NULL
);
```

日数の3列（`planned_days` / `actual_days` / `covers_from`）と `kakeibo_forecast_basis` テーブルは**作らない**。予想が名称ごとの周期を持たなくなったので、置き場所が無い。

**v30 を分割しない理由**: この change はまだ1度もコミットされていない。マイグレーションは `user_version` の昇順でしか流れないので、旧 v30 を適用済みのローカル開発 DB は**作り直す**（未リリース機能なので失うデータは無い）。ここで v31 を積むと、リポジトリには最初から誰も通らない中間スキーマが永久に残る。

**代替案（`kakeibo_entry` に月・週の集計列を持たせる）を採らない理由**: 特別費はいつでも切り替えられる。切り替えた瞬間に1日平均が変わり、1日平均が変われば予想が変わり、予想が変われば上限超過日が変わる。集計を保存すると、この連鎖の全段に無効化処理が要る。1か月の `kakeibo_entry` はたかだか数十行なので、**毎回その場で計算する**。

### D2. 予想は「1日平均ひとつ」。名称ごとの周期を持たない

```
日々の出費 = Σ(その月の kakeibo_entry のうち特別費でないもの)
1日平均    = floor(日々の出費 ÷ 経過日数)      -- 経過日数は今日を含む
残りの予想 = 1日平均 × 残り日数                -- 残り日数は翌日から月末まで
月末予想   = 固定費 + 変動費の実績（特別費を含む）+ 残りの予想 + 残り日の予定出費
```

カテゴリで分岐しない。名称で分岐しない。買い方（まとめ買いか都度か）でも分岐しない。**コンビニだろうがまとめ買いだろうが同じ母数に入る**。

**分子は月の日数**（28〜31）であって 30 ではない。issue コメントの「30/現在の日数」は概数で、30 を固定にすると2月で按分が 7% 狂う。

**4巡目のモデルを捨てた理由**: 名称ごとの日単価は「その買い物が何日もったか」をユーザーに聞かないと出せない。聞くための1問モーダル・未確定という第3の状態・後から直すための一括編集ビュー・どの基準で平均するかの4択と、そのすべてを説明する画面が要る。得られる精度に対して、ユーザーが払う入力コストと実装量が釣り合わない。単純按分は**入力ゼロ**で出る。

### D3. 特別費は「カテゴリで自動」＋「手で上書き」。実績には残す

```
除外される = (category = 'SUDDEN') OR (is_special = 1)
```

`is_special` は**手動フラグだけ**を保存し、`SUDDEN` の自動判定は保存しない。カテゴリを後から変えたら除外も追随してほしいので、**都度導出する**のが正しい（保存すると、急な出費から食品へ直したときに除外が取り残される）。

- 自動（`SUDDEN`）: UI では二択が選択済み・**操作不可**で出る。手で通常へ戻せない
- 手動（`is_special`）: 記録カード（`X`）・履歴の行・調整モーダルのどこからでも切り替えられる

**外した額は実績に残す**。月の合計・カテゴリ合計・重要度の帯・分析には従来どおり入り、1日平均の母数からだけ抜ける。歯医者に行った事実は消えない。消えるのは「毎日歯医者に行く前提で月末を予想する」ことだけである。

**保存の意味が2つある**のは意図的である。ホームの調整モーダルは複数レコードを並べた **what-if** なので、切り替えても保存せず「これで予想する」で確定する。履歴の行の二択はレコードの直接編集（カテゴリを直すのと同じ）なので**その場で保存する**。

### D4. 単純按分が上振れすることを、演出で覆い隠さない

8/11 時点のモックで、旧モデルの着地は ¥65,670、新モデルは **¥77,010**。差の原因は月前半のまとめ買い（業務スーパー ¥4,200 が数日分）を31日ぶんへ引き伸ばすことにある。これは方式の性質であって不具合ではなく、月が進むほど収束する。

設計上の帰結が2つある。

1. **数字を作って判定をひっくり返さない**。旧モックの見せ場は「基準を変えると上限内へ戻る」だったが、新モデルでは何を特別費にしても上限内には戻らない。特別費で縮むのは超過幅（¥15,010 → ¥8,670）であって符号ではない。デモの数字を上限内に収まるよう調整することはしない
2. **月初は極端に振れる**。1日目に ¥5,000 使えば月末予想は ¥155,000 になる。ここに下駄（最低経過日数など）を履かせると式が説明できなくなるので、**入れない**。振れることを受け入れ、緩和は特別費の指定に委ねる（Open Questions）

### D5. 月末予想は閉じた式にせず、残り日を1日ずつ歩いて積む

```
series[d] = 固定費 + 実績累計(d)                  … d <= 今日
series[d] = series[d-1] + 1日平均 + その日の予定出費 … d > 今日
```

上限超過日は `series` を前から見て初めて `cap_yen` を超える日である。

**代替案（`(上限 − 実績) ÷ 1日平均` の割り算で求める）を採らない理由**: 予定出費（8/20 の ¥1,800）が段として乗るので、線は一次関数ではない。割り算だと段の前後で答えがずれる。日数はたかだか31なので、素直に歩くほうが正しく、読める。

`series` はサーバが返す。折れ線の SVG はこの配列を写すだけにして、クライアント側で予想を再計算しない（2箇所に同じ式があると必ずずれる）。

### D6. 丸めは「金額＝切り捨て」「割合＝四捨五入」の2系統だけ

- **1日平均・金額**: `floor`（1円単位）。`19,350 ÷ 11 = 1,759.09… → 1,759`
- **予算由来の「目安」**: `floor10`（10円単位）。週の目標 `44,620 ÷ 31 × 7 = 10,075.5 → 10,070` / 1日あたり `8,170 ÷ 6 = 1,361.67 → 1,360`

**先に丸めてから掛ける**。月末予想は `floor(1日平均) × 残り日数` であって `floor(日々の出費 ÷ 経過日数 × 残り日数)` ではない（`1,759 × 20 = 35,180`、`35,181` ではない）。画面に出ている1日平均と月末予想が算数として合っていないと、ユーザーは数字を信じるのをやめる。

**割合（%）だけは四捨五入**する。`4,920 ÷ 22,650 = 21.72% → 22%` / `11,950 ÷ 22,650 = 52.76% → 53%` / `6,800 ÷ 9,340 = 72.8% → 73%`。金額を切り捨て、割合を四捨五入するのは、**金額は「これ以上使える」の上限として使うので少なめに出すべき**なのに対し、**割合は比較のための表示でしかない**ためである。

### D7. 予算は月ごとの行。週の目標は保存せず導出する

```
変動費に使える = cap_yen − Σ fixed_cost(月)
週の目標       = floor10(変動費に使える ÷ 月の日数 × 7)
今週の残り予算 = 週の目標 − 今週の変動費実績
```

週は**月曜始まり**（モックの `8/10 – 8/16`、今日 8/11 火）。残り日数は今日を含む（`8/11..8/16 = 6日`）。

**代替案（週の目標を保存する）を採らない理由**: 月の上限か固定費を直した瞬間に古くなる。導出なら常に整合する。

固定費の「7月から取り込む」は前月の `kakeibo_fixed_cost` 行を**名前と金額ごとコピー**するだけ（実績ではなく前月の予想を引き継ぐ）。既に同じ名前の行がある月へは入れない（`UNIQUE(month_key, name)`）。

### D8. 予定出費は予想にだけ入り、記録した瞬間に実績へ置き換わる

`kakeibo_planned_expense` の行は `kakeibo_entry` を1行も作らない。予想の `series` に段として乗り、記録カードにチップとして出るだけである。チップを押すと目安金額が入った状態の入力になり、実際の金額で記録すると:

1. 通常の `kakeibo_entry` が1行できる（＝実績）
2. その予定出費の `next_day_key` が `cycle_days` 分進む
3. 今月の予想からその段が消える（実績が段の代わりになるので二重計上しない）

**「予想に入れた金額」を実績に混ぜてはいけない**。混ぜると、まだ払っていない床屋代が「使った額」に化ける。実績はレシートが存在するものだけである。

### D9. まとめ登録は「名称なし・重要度なし」として、名称別分析の母数から外す

未記録期間の一括入力（#94「長い間未記録だったとき」）は `name = ''` / `importance = NULL` / `bulk_from`・`bulk_to` 非 NULL で表す。

- 月の合計・カテゴリ合計には**入る**（実際に使った金額だから）
- **1日平均の母数にも入る**（`is_special = 0`）。実際にその期間に使った金額なので、日々の出費として扱うのが正しい
- 重要度の帯には `内訳未入力` として**独立した区画**で出る（必須/準必須/無駄遣いのどれにも混ぜない）
- 名称別のドリルでは `名称なし` の1行にまとまり、そこで止まる

**「分からない」を「必須」や「無駄遣い」に割り振らない**。まとめ登録は、内訳が失われた事実の記録である。推測で埋めると、無駄遣い率という一番大事な数字が嘘になる。

### D10. 内訳は自由記述。レシートと同じ場所に、別々の面で出す

`detail TEXT`（NULL 可）。#94 の「レシートはないけど何を買ったのか覚えているとき」がそのまま要件で、**システムは中身を解釈しない**（パースして品目集計などはしない。やるなら別 issue）。

見る場所は**レシートと同じ**＝明細のモーダル。ただし内訳（本人が書いた文字）とレシート（写真）は**別々の面に分ける**。混ぜると「レシートに書いてあったこと」と「思い出して書いたこと」の区別が付かなくなり、証拠としての価値が落ちる。片方しか無いときは、無いほうを「無い」と明示する。

このモーダルは**履歴の行からも分析の明細からも同じものが開く**。押下可否の条件も同じ ― `内訳もレシートも無い行は押せない`。ただし押せないことを**減光では表さない**（`[disabled]` の既定の減光が効くと、記録そのものが無効に見える。実測でそう見えた）。

### D11. ゲートは `PLANNING` の新シグナル。0円宣言は別テーブル

`PLANNING_SIGNAL_KEYS` に `kakeibo_recorded` を足し、`resolvePlanningSignal` の `switch` に1本追加する:

```
kakeibo_recorded = (その day_key の kakeibo_entry が1件以上) OR (kakeibo_zero_day にその day_key がある)
```

**代替案（新しい `RuleTarget = 'KAKEIBO'` を作る）を採らない理由**: `RuleTarget` を増やすと `packages/contract` の enum・`evaluate.ts` の `switch`・`rule-form.js` の種類選択・`targets.js` のラベル・沿革の表示が全部増える。求めているのは「ブール1個」なので、既にブール1個のために用意されている `signal_key` の受け口を使う。

**「0円だった」を別テーブルにする理由**: 金額0の `kakeibo_entry` を作ると、それが分析の明細に「¥0 の買い物」として並び、名称も重要度も無いのに件数だけ増える。宣言は支出ではないので台帳に入れない。

### D12. レシートは専用テーブル。`goal_journal_image` は再利用しない

`goal_journal_image` は `goal_id INTEGER NOT NULL REFERENCES goal(id) ON DELETE CASCADE` で、目標が消えると画像も消える。レシートは目標と無関係なので、ダミーの `goal` を作るか NOT NULL を外すかしかなく、どちらも既存の意味を壊す。

`kakeibo_receipt` を作り、`kakeibo_entry.receipt_id` から `ON DELETE SET NULL` で参照する（画像を消しても支出の事実は残す）。アップロードは `static/js/images.js` の `shrinkImage()` をそのまま通す（**外部送信ゼロ・ローカル完結**は既存の約束）。

### D13. 金額はすべて整数円。小数を持ち込まない

`amount_yen` は `INTEGER`。1日平均も整数（D6 で floor）。SQLite の `REAL` は使わない。

### D14. サーバは「画面1つにつきエンドポイント1つ」で返す

```
GET  /api/kakeibo/home?month=YYYY-MM        → { series, landing, summary, week, waste, plannedChips }
GET  /api/kakeibo/history?month=YYYY-MM     → { entries }
GET  /api/kakeibo/analysis?month=YYYY-MM    → { importance, tree }
GET  /api/kakeibo/budget?month=YYYY-MM      → { budget, fixedCosts, plannedExpenses, derived }
GET  /api/kakeibo/forecast-adjust?month=    → { rows, effect }   -- 調整モーダルの一覧
POST /api/kakeibo/forecast-adjust/preview   → 保存せずに effect を出し直す（D3）
POST /api/kakeibo/entries                   → 記録
PATCH/api/kakeibo/entries/:id               → 金額・カテゴリ・重要度・特別費・内訳・レシートの修正
POST /api/kakeibo/entries/bulk              → 未記録期間の一括入力
POST /api/kakeibo/zero-day                  → 「0円だった」
POST /api/kakeibo/receipts                  → 画像（data URL）
GET  /api/kakeibo/receipts/:id              → 画像バイト
GET  /api/kakeibo/names?prefix=             → 名称サジェスト
```

**画面が要るものを1回で返す**。ホームは折れ線・1行サマリ・週の残り・無駄遣い・予定チップを同時に出すが、これらは全部同じ月の同じ `kakeibo_entry` から出る。5回叩くと5回同じ行を読むうえ、途中で特別費を切り替えたときに画面の一部だけ古くなる。

`preview` を保存と分けるのは、モックの「切り替えると4つの数字が同時に出し直される」を**保存前に**見せるためである（`これで予想する` を押すまで確定しない）。履歴の行の二択は `PATCH /entries/:id` を直接叩く（D3）。

### D15. フロントは月とサブタブの2つだけを状態に持つ

`kakeibo.js` が `{ month, view }` を持ち、どちらかが変わったら該当エンドポイントを叩き直して描き直す。折れ線・ツリーは**サーバの返り値を写すだけの純描画**にする。第5のビュー（日数の一括編集）は無くなったので、`view` は `home|hist|ana|budget` の4値。

### D16. 履歴の行は「左＝明細を開くボタン / 右＝二択」の2領域

行そのものをボタンにすると、中の二択が `<button>` の入れ子になって不正な HTML になる。二択を**兄弟要素として外に出す**ことで、`stopPropagation` に頼らずに押し分けが成立する。

```html
<div class="kb-hist-row">
  <button class="kb-hist-main" data-open="detail"> 日付 名称 金額 カテゴリ 重要度 印 </button>
  <span class="kb-toggle"> 通常の出費 | 特別費（除外） </span>
</div>
```

**履歴にグラフを置かない**。4巡目のカバー期間の帯も、5巡目で一度置いた日ごとの支出の棒も落とした。推移はホームの折れ線が担っており、履歴で見たいのは個々の記録である。

## Risks / Trade-offs

- **単純按分が月前半で上振れする** → D4 のとおり隠さない。緩和は特別費の指定だけ。月が進めば収束する
- **月初（経過1〜3日）は予想が極端に振れる** → 下駄を履かせない（式が説明できなくなる）。Open Questions に残す
- **特別費の手動指定が面倒／付け忘れる** → 急な出費は自動で外れるので、手動が要るのは「食品カテゴリの年1回のまとめ買い」のような例外だけ。記録カード（`X`）・履歴の行・調整モーダルの3箇所から切り替えられる
- **特別費を付けすぎると予想が実態より低く出る** → 除外した合計を1行サマリに `特別費: ¥3,300` として常時表示し、調整モーダルで一覧できるようにする（黙って消えない）
- **折れ線の SVG を手で書く** → Chart.js は既に vendored されているが、要素は「線3本・段・点2つ・帯1つ」だけで、階段はプラグイン無しでは素直に描けない。素の SVG のほうが短い。`viewBox` は全幅前提の `700×300` に固定し、レスポンシブは `width:100%` に任せる
- **`app.css` が肥大する** → `kb-` 接頭辞で家計簿固有のものだけを足し、面・線・角丸・ボタン・モーダルは既存トークンを継承する。**1ルール1行の既存書式を守る**（フォーマッタを全体にかけない＝プロジェクトルール）
- **タブが6本になって数字キーが1つ増える** → `main.js` は `Math.min(9, tabs.length)` なので自動で追随する。`shortcut-hints.spec.ts` は propose 側で直す
- **カテゴリ4色の可読性** → dataviz の `validate_palette.js` で検証済み（light・白面・明度帯/彩度/CVD隣接/コントラスト 全 PASS）。重要度は色を増やさず `塗り / 薄塗り / 45°斜線 / 点線` で表す

## Migration Plan

マイグレーション v30 は `CREATE TABLE` 6本のみで、既存行のデータ移行は無い。既存 DB を開くと空のテーブルが6本増えるだけで、家計簿タブを開かない限り何も起きない。ロールバックは「タブを出さない」だけで足りる（テーブルが残っても他の機能は参照しない）。

**旧 v30（日数モデル）を適用済みのローカル開発 DB は作り直す**。`user_version` は昇順でしか流れないので、同じ v30 の SQL を書き換えても再実行されない。未リリース機能なので失うデータは無い。

`kakeibo_recorded` シグナルを使うルールを**自動では作らない**。ユーザーが設定から明示的に追加したときだけゲートに現れる。既存ユーザーの解錠条件を勝手に増やすと、ある朝突然パスワードが出なくなる。

## Open Questions

- **月初の振れをどうするか**: 経過1〜3日では1日平均のぶれが大きく（1日目に ¥5,000 で月末予想 ¥155,000）、予想としては使いにくい。今回は下駄を履かせず、そのまま出す。運用してみて耐えられなければ「経過N日未満は前月の1日平均を使う」「予想を出さずに『まだ判断できない』と出す」などを別 issue で検討する
- **月をまたいだ出費の扱い**: 7/26 に買って8月まで使った分は、**買った日の月に全額**を計上する（レシートの日付＝出費の日）。日数を持たなくなったので按分の余地がそもそも無い
- **特別費が積み上がったときの棚卸し**: 手動の特別費は解除されない限り残る。翌月へは持ち越さない（月ごとに `kakeibo_entry` を見るので自動的にリセットされる）が、同じ名称を毎月手で外し続ける運用になったら、それは「名称ごとの既定」を持つべきサインである。今回は作らない
