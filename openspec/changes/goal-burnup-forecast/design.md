## Context

進行中の目標を開くと `renderReport()` が呼ばれ、完走後の振り返り用に作った5ブロック（①達成カレンダー ②時間の推移 ③写真の比較 ④日記ストリップ ⑤沿革）がそのまま出る。走っている最中に知りたい「いつ終わるのか」はどこにも無く、③④は素材が溜まっておらず、Check を続ける動機が生まれていない。完走後に開いても同じで、本人が「見たい要素が一つも入っていない」と判断している。したがってこの変更では**レポートを直すのではなく廃止**する。

一方で材料は既に揃っている:

| 材料 | 現在地 |
|---|---|
| 目標配下の親子タスク（容れ物と葉） | `task.parent_task_id` / `goal_id` / `tree_order`（`task-tree`） |
| 目標に紐づく作業時間の累積 | `goals.ts` の `accumulatedSecondsFor(db, row, dayKeys)` |
| 計測対象の指し方 | `goal_target_hours` + `goal_target_hours_member`、および目標に紐づく時間型ルール |
| 凍結期間 | `goalFreezeIntervals()` |
| 進行中／完走後の分岐 | `goalCard()` のボタン文言分岐（`goals.js:258`） |

足りないのは **残り想定時間（スコープ）** だけで、それは正確に測れる種類の数字ではない。ユーザーは Gemini と雑に合議して決めることを望んでおり、アプリはその数字を検算せずそのまま使う。

## Goals / Non-Goals

**Goals:**

- 目標を開いたとき、完了予想日が主役の1枚だけを出す（レポートは廃止し、ビューを1つに減らす）
- 完了予想日が **毎日動く**（累積は単調増加なので、必ず何かが動く）
- 完了予想日を手前へ動かす手が2系統ある（積む／削る）ことが画面で読める
- これまで何を終えたかを、累積線の上のタスク達成マーカー（黒丸＝完了・白丸＝進行中の枝）で追える
- 広い期間表示から日付をクリックして絞り込め、日単位まで拡大したら日付クリックで振り返り（作業時間バー＋本文）をモーダルで開き、その場で編集・保存できる
- Gemini / Antigravity が HTTP 経由で見積もりを書き込める

**Non-Goals:**

- 見積もりの正確性。単価も仮置きも「それっぽい」で十分であり、精度を上げる仕組みは作らない
- 解錠ゲートへの合流。バーンアップは `unlock_evaluation` に一切現れない
- 複数の枝を同時に走らせること。走行中の枝は常に1つ
- ①③④⑤ に相当する画面の作り直し（廃止するだけで、移設先は用意しない）
- 夜のリザルト画面・通知など、進捗グラフを開く以外の出口
- 目標の期限（`end_day`）との比較表示。`end_day` は完走フォーク・再開・終了のたびに動く運用上の値であり（`goal-lifecycle-fork`）、進捗グラフへ固定の締切として描かない（D7 参照）
- **残り想定（スコープ）の段差・変更履歴をグラフ上に可視化すること**。予測の計算にだけ使い、理由や実行者は画面には出さない（D11 参照）。ちらつく段差だらけの線より、達成マーカーの方が「何をやったか」を素直に示す
- **完了予想の推移（過去にどう動いたか）の追跡**。今日時点の2ペースを見せるだけで、予想日がどう動いてきたかの履歴チャートは作らない

## Decisions

### D1. レポートは capability ごと消す。ビューは進捗グラフ1つ

目標を開いたときの行き先を**進捗グラフ1つ**にする。レポート画面・`GET /api/goals/:id/report`・①〜⑤のブロック関数をすべて削除する。

```
today <  start_day  → 開けない（409）
today >= start_day  → 進捗グラフ（進行中は完了予想あり／完走後・終了後は無し。累積線とタスク達成マーカーはどちらの場合も描く）
```

目標カードのボタンは4つ（レポートプレビュー／タスク一覧／終える／削除）で、数を増やさない。文言だけ差し替える。

```
進行中  「進捗グラフ」 ／ タスク一覧 ／ 終える ／ (削除)
完走後  「続ける」 ／ タスク一覧 ／ 終える ／ (削除)
```

**代替案**: 進行中だけ差し替えて完走後はレポートを残す → 却下。完走後も開く動機が無いと本人が判断している。残すと①〜⑤の保守が続き、進捗グラフと二重の読み手になる。
**代替案**: 「進捗グラフ」を第3のビューとして足す → 却下。カードの導線が5つになる。
**代替案**: 既存 E2E 3本が到達手段を失うのでレポートを残す → **却下**。E2E は仕様どおりかを確かめる手段であって、仕様を決める理由にならない。レポートしか検証していない2本は削除し、レポート経由で別の対象を見ていた2本はその区間を落とす。

### D1-b. フォークだけは落とせないので目標カードへ移す

レポートの中で唯一、表示ではなく**機構**なのが「続ける／終える」フォーク。答えるまで永続ルール（`end_day=null`）がゲートに残り続ける（`goal-lifecycle-fork`）ため、提示場所を失うと未回答の目標のルールを外す手段が消え、ゲートが永久に開かなくなる。

移設先は**目標カード**。完走カードの「レポートを開く」の位置に「続ける」が入り、既存の「終える」と2択になる。導線の数は変わらず、未回答の目標が一覧で目立つという副次効果もある。実装も既存を流用できる（「終える」＝`openEndDialog`、「続ける」＝`POST /api/goals/:id/continue`）。

### D1-c. 消える情報を正直に数える

レポートの廃止で**画面から読めなくなるもの**:

| 失うもの | 出どころ | 代替 |
|---|---|---|
| ①達成カレンダー・達成 N/M | `unlock_evaluation` | 無し（レコードは残る） |
| ③写真の比較 | `goal_journal_image` / `rule_answer` | 大きい沿革の終了・完走の行（Before→After） |
| ④日記ストリップ | `goal_journal` | 振り返りタブの目標コーナーで読み書き（`goal-journal`） |
| ⑤沿革（ルール操作の理由・凍結・答え合わせ） | `rule_change` / `rule_answer` / `goal_freeze_change` | **無し** |
| ①のマスから開く日別詳細 | 同上 | 振り返りタブ（`reflection-journal`） |

⑤の喪失が一番大きい。大きい沿革（`goal-history`）は「ルール操作・凍結イベント・日記を載せてはならない（MUST NOT）」と規定されており、引き取らない。**レコードは1件も消さない**ので、必要になった時点で別の画面へ出せる。

### D2. 計測対象は既存の指定から解決し、無いときは空状態にする

バーンアップの縦軸は累積作業時間なので、「何の時間を積むか」が要る。新しい指定枠は作らず、次の順で解決する。

1. `goal_target_hours` の対象（`kind` と members）— `seconds_per_day` は**使わない**（1日あたりの目標は別の意図の数字）
2. 目標に紐づく**時間型ルール**（`TOTAL_WORK` / `GROUP` / `TIMELINE`）の対象を束ねる
3. どちらも無ければ **空状態**（「何で測るかを決める」導線）

`goal-target-hours` の「目標時間の有無で処理を場合分けする例外（レポート構成の変更等）を設けてはならない（MUST NOT）」に抵触しないよう、**ブロックは常に出す**。目標時間を持たない目標でも進捗グラフのビューは同じ構成で開き、中身が空状態になるだけとする。構成が変わるわけではない。

**代替案**: 目標時間を持つ目標にだけバーンアップを出す → 却下。上記 MUST NOT に正面から当たる。
**代替案**: 対象が無ければ全作業時間（`TOTAL_WORK`）へフォールバック → 却下。Udemy の目標に家計簿をいじった時間が混ざり、予想が静かに壊れる。

### D3. 凍結日はバーンアップでは 0h として数える。`goalPace()` は変えない

バーンアップは**暦どおり**に日を数え、凍結日も 0h の実績として累積線に含める。凍結で予想日が遠のき、復帰後に直近3日ペースが跳ねて大きく縮む — この谷と戻りが報酬になる。

一方、既存の `goalPace()`（目標時間のペース表示）は凍結日を分母から除いており、`goal-target-hours` にその要件がある（「凍結日を分母に数えてはならない・MUST NOT」）。**これは変更しない。**

同じ画面上に定義の違う2つの平均が並ぶことになるため、意味の違いをラベルで明示する:

| | 数える日 | 問い |
|---|---|---|
| 目標時間のペース（既存） | 凍結日を除く | 1日あたりの目標を守れているか |
| バーンアップのペース（新） | 凍結日を含む | 実際の暦でいつ終わるか |

**リスクとして残る。** 下の Risks に再掲する。

### D4. 想定時間は容れ物に持たせ、変更は別テーブルに追記する

```sql
ALTER TABLE task ADD COLUMN estimated_seconds INTEGER;      -- NULL = 未設定
ALTER TABLE task ADD COLUMN progress_ratio REAL;            -- 葉のみ・NULL = 未設定（done なら 1.0 扱い）

CREATE TABLE task_estimate_change (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  task_id INTEGER NOT NULL REFERENCES task(id),
  field TEXT NOT NULL,              -- 'estimate' | 'progress'
  from_value REAL,
  to_value REAL,
  reason TEXT NOT NULL,
  actor TEXT NOT NULL,              -- 'human' | 'agent'
  day_key TEXT NOT NULL,
  created_at INTEGER NOT NULL
);
```

`practice_threshold_change` / `rule_change` / `goal_freeze_change` と同じ「値は本体、履歴は別テーブル」の流儀に合わせる。理由を必須にするのは `goal-blueprint` の枝の打ち切りと同じ考え方で、段差の意味が後から読めなくなることを防ぐ。

**マイグレーションは新しいバージョンを足す。既存 migration の SQL を書き換えない**（過去に2回、書き換えたせいで実 DB へ反映されない事故が起きている）。

### D5. 走行中の枝は「未完了の葉を持つ、根直下の最初の枝」

`tree_order` 順に根直下の枝を見て、未決着の葉を持つ最初の枝を走行中とする。同時に2つは走らない。2つ同時に進めたい日があっても、そのためにロジックを複雑にしない（ユーザー決定）。

枝の**開始日**は、直前の枝が決着した日の翌日。直前の枝が無ければ目標の `start_day`。

### D6. 単価は走行中の枝でだけ実測から導き、仮置きを上書きする

```
枝の実測秒   = 枝の開始日〜今日の累積秒
枝の消化量   = その枝で完了した葉の重み合計（done = 1.0、未 done は progress_ratio）
単価         = 枝の実測秒 ÷ 枝の消化量
枝の残り想定 = 単価 × 残りの葉の重み合計
```

消化量が 0 のとき単価は出せないので、**Gemini の仮置き（`estimated_seconds`）をそのまま使う**。消化量が 0 より大きくなった時点で、実測由来の値が仮置きを上書きする。

これが提案の「要因3（単価の改善）」の実体で、**同じ時間だけ働いたのに予想が余計に縮む日**を作る。慣れて速くなったことが自動で報酬になる。

先の枝（まだ走っていない枝）は常に仮置きのまま。実測が無いので導きようがない。

**代替案**: 全枝で単価を導く → 却下。作業時間は枝ごとに分かれて記録されておらず、走行中の枝が1つだからこそ期間で切り出せる。

**この残り想定（スコープ）は進捗グラフには描かない。** D7 の完了予想日の計算にだけ使う。当初案は段差つきの「スコープ線」として可視化する予定だったが、実装前のモック検証で「線が増えるほどごちゃつく」と判断し、可視化は D11 のタスク達成マーカーに置き換えた。`task_estimate_change` の理由・実行者は記録として残すが、読み手（画面）は当面用意しない（`goal-chronicle` と同じ扱い）。

### D7. ペースは2本。全体平均と直近3日

```
全体平均 = 目標開始日〜今日の累積秒 ÷ 経過日数（凍結日を含む・今日を含む）
直近3日  = 直近3日の累積秒 ÷ 3（今日を含む）
```

完了予想日は、残り想定秒をペースで割った日数を**切り上げて**今日へ足した日。家計簿の月末予想が「日単価を先に整数へ切り捨ててから掛ける」と決めたのと同じ理由で、画面に出ている数字と算数が一致することを優先する。

**画面の主役は完了予想日そのもの（絶対日付）で、選んだペースの数値切り替えは「全体平均ペース／直近3日ペース」のトグルで行う。** 選ばれていない側も、太字ではない細い線と小さいラベルで残す（比較できないと「早まった」が実感できないため）。**予想の推移（過去にこの日付がどう動いてきたか）は追跡・表示しない。** 今日という1時点の2ペースだけを見せ、履歴のグラフやスパークラインは作らない——過去の予想がどうだったかより、今日から見てどうかの方が行動に直結するため。

ペースが 0（その期間に一切積んでいない）のとき、完了予想日を**出さない**。0 除算の表示を出してはならないという `kakeibo-forecast` の既存判断に合わせる。

完了予想日を目標の期限（`end_day`）と比較する表示は行わない。`end_day` は完走フォーク・再開・終了のたびに動く運用上の値であり（`goal-lifecycle-fork`）、固定の締切として描くと「結局いつでも動かせるものを壁のように見せる」ことになり、見通しの信頼を損なう。画面が主役として示すのは完了予想日そのもの（絶対日付）であり、「あと n 日」は補助情報にとどめる。

**代替案**: 期限を越えた場合に警告表示する → 却下。`end_day` は本人の判断で好きに伸ばせる・早められる値であり、超過を大きく見せることは実態と合わない情報になる。

### D8. 描画はインライン SVG。実装は `ref/goal-burnup/burnup-mock.html` を参考にする

リポジトリには `chart.umd.min.js`（家計簿で使用）があるが、バーンアップに必要なのは折れ線ではなく **タスク達成マーカー（黒丸・白丸・注釈）・予測直線（太い破線＋丸／細い点線）・月→日のズーム帯・日付クリックの当たり判定**で、Chart.js では注釈プラグイン無しに置けない。

インライン SVG で描き、Chart.js は家計簿のまま触らない。

**実装の参考として `ref/goal-burnup/burnup-mock.html` を用意した**（静的モック。ユーザーとの対話で複数回イテレーションして固めた最終形）。配色・情報設計・インタラクションはこのモックに合わせる SHOULD:

- タスク達成マーカー: 完了した根直下の枝＝黒丸＋常時注釈、走行中の枝＝白丸＋常時注釈（クリックでその枝の葉一覧をモーダル表示）、完了した葉＝小さい黒丸（クリックで詳細モーダル）。同じ日に複数の葉が完了した場合は1つの丸にまとめ、クリックでその日の一覧を出す
- 完了予想: 選んだペースだけ太い破線＋丸＋日付ラベル、もう一方は細い点線＋小さい日付ラベルのみ（丸は出さない）
- 今日の位置は、横軸には**今日の日付**、縦軸には**実測時間**を薄い点線で引いて示す（両方を1つのラベルに詰め込まない）
- ズーム: 表示期間が約40日を超えるときは月単位の帯を表示し、クリックした月（前後3日を含む）へ絞り込む。約40日以下になったら日単位の帯に切り替わり、日付をクリックすると振り返りタブへの導線を出す
- DOM 構造やクラス名まで一致させる必要はないが、上記の挙動・情報設計・視覚的な強弱（強調⇄控えめ）は一致させる SHOULD

### D9. 書き込みは既存の HTTP API 経由のみ。アプリは検算しない

```
GET  /api/goals/:id/burnup          進捗グラフ1枚ぶんの数字（サーバで計算済み）
PUT  /api/tasks/:id/estimate        { estimatedSeconds, reason }
PUT  /api/tasks/:id/progress        { ratio, reason }
```

`GET /api/goals/:id/burnup` は**計算済みの値**を返す。クライアントは描画に徹する（`kakeibo-forecast` の「予想の計算はすべてサーバが行い、クライアントは描画に徹する」と同じ）。レスポンスには累積線の点列・2ペースの完了予想日・タスク達成マーカー（根直下の枝＝名前／完了日 or 進行中／その葉一覧）を含める。**残り想定の値そのものや変更履歴は含めない**（D6 参照。予測日はサーバ側の計算で既に織り込み済みのため、クライアントに渡す理由が無い）。

`PUT` は `reason` を必須とし、`task_estimate_change` へ1行追記する。`actor` はリクエスト元ではなく**明示的に渡させる**（誰が決めたかは画面に出る情報であり、推測させない）。

zod スキーマは `packages/contract/src/index.ts` に置く。外部エージェントが叩く口なので、型の drift をここで止める。

**アプリは受け取った数字を検算しない。** `ratio` が 0.8 でも 1.0 でも、それがどう決まったかには関知しない。柔軟性は「数字の決め方」の側に閉じ込め、算数は硬いままにする。

### D10. バーンアップは解錠ゲートに一切合流しない

`unlock_evaluation.per_condition_results` にバーンアップ由来のエントリが現れてはならない。完了予想日が遠のいてもパスワードは出る。`goal-target-hours` が同じ判断を既にしており、理由も同じ（当日評価と両立しない・下限とゴールの二段構えが消える）。

### D11. タスク達成マーカーで「何をやったか」を追う。親は常時注釈、子はモーダル

累積線の上に、根直下の枝（親タスク）と葉（子タスク）の完了を丸で示す。

```
親（根直下の枝）:
  完了   → 黒丸 + 常時注釈（枝名）
  走行中 → 白丸 + 常時注釈（枝名「（進行中）」）+ クリックでその枝の葉一覧をモーダル表示
  未着手 → 何も描かない（時間軸上の根拠が無いため）

子（葉。走行中の枝のものだけが対象。design D5 により走行中の枝は常に1つ）:
  完了   → 小さい黒丸（実際の完了日の位置）+ クリックで詳細モーダル（名前・状態・完了日）
  未完了 → 丸を描かない。走行中の枝の白丸をクリックしたときのモーダル一覧でだけ読める
```

同じ日に複数の葉が完了した場合は**1つの丸にまとめ**、クリックするとその日に完了した全件をモーダルで一覧表示する SHALL する。丸を隣り合わせに並べてはならない（MUST NOT）。

**代替案**: 未完了の葉も白丸で個別に描く → 却下。実装前のモックをユーザーに見せたところ、「進行中の枝の白丸の隣に未完了の葉の白丸が並ぶと、どちらが何を指すか分からない」というフィードバックを受けた。未完了の葉は日付の根拠が無い（まだ終わっていないので「いつ」に置きようがない）ため、枝の白丸へ集約してモーダルで見せる形に変えた。

**代替案**: 親も子も同じ扱いで注釈する → 却下。全部に注釈を付けるとグラフがラベルで埋まる。親（根直下の枝）は数が少なく、走っている大筋を示すので常時注釈に値するが、葉は数が多いためクリック起点のモーダルに留める。

### D12. 広い期間は月単位の帯、クリックで期間を絞り込む

進捗グラフの初期表示は目標の `start_day` 〜（原則）今日から少し先までの全期間。表示期間が**約40日を超える**ときは月単位の帯（クリック領域）を月ごとに敷き、クリックするとその月（前後3日を含む）へ表示範囲を絞り込む。「← 全期間に戻す」で元に戻せる。

ズームは**クライアント側だけで完結**させる SHALL する。`GET /burnup` は最初から全期間ぶんのデータを返しており、ズームは既に取得済みのデータを再描画するだけで、サーバへ追加のリクエストを発行しない SHALL する（期間ごとに API を叩き直すと、月をまたぐクリックのたびに待ちが生まれる）。

### D13. 日単位まで拡大したら、日付クリックで振り返りをモーダルで開く

**（実機確認後の改訂・issue #106）当初はタブ遷移としていたが、この決定を覆す。** このアプリは一画面設計であり、振り返りタブへ飛ばされると進捗グラフへ戻る手間が大きいと実機確認で本人からフィードバックがあった。表示期間が**約40日以下**になったら、月の帯の代わりに日単位の帯を敷く点は変わらないが、日付をクリックすると**タブ遷移せずモーダルを開く** SHALL する。

モーダルの中身は2つ:

1. **その日の作業時間バー** — 振り返りタブにある `reflection.js` の `buildAllocCard()` と同じ見せ方
2. **その日の振り返り本文** — 閲覧・編集・保存ができる（振り返りタブの本文エディタと同じ体験）

実装は `reflection.js` から `buildAllocCard()` と本文エディタ（`loadEditorForDate()` 相当）を**共有部品として export**し、進捗グラフ側のモーダルから呼び出す。保存は既存の `PUT /api/reflection/:date` をそのまま叩き、**新しい API は起こさない**。振り返りタブ側の挙動・DOM は変えない（同じ部品を2箇所から呼ぶだけ）。

旧決定時点の却下理由「二重実装になる」は、エディタを共有部品として export する実装方針を取ることで解消される（実体は1つ、呼び出し口が2つ）。旧仕様の `goToReflectionDay()` とその日付ストリップ deep-link 機構は、呼び出し元が無くなるため削除する。

**代替案**: タブ遷移のまま残す → 却下。実機確認で「一画面設計のアプリで戻る手間が面倒」と明確な却下理由が本人から示された。
**代替案**: モーダルに振り返りタブの全機能（画像添付・気分入力等）を持たせる → 却下。今回のフィードバックは「作業時間バーと振り返りの閲覧・編集・保存が見えればOK」であり、範囲を広げると新規 e2e が膨らむ。画像添付等が必要になった時点で別途検討する。

### D14. ラベル配置は衝突回避の1パスで行う（表示バグ修正・実機確認後の追記・issue #106）

実機確認で、達成マーカー注釈・完了予想ラベル・実測時間サブラベル（`${lastHours.toFixed(1)}h`）が固定オフセット直書き（例: `x+9, y-9`）のため、他要素や累積線と重なって読めない箇所が見つかった。これは D11・D7・D6 で規定した**見せ方そのものの変更ではなく**、その描画の実装バグである。したがって新しいシナリオは追加しない。

修正方針:

1. その回の描画で配置予定の全ラベルの候補位置を先に集める（1パス）
2. 既に描画確定した矩形と重なる場合は、上下方向へずらして衝突を避ける
3. プロット領域の右端に近い場合は、アンカーを左側へ反転する
4. 累積線の描画パスに重なる場合は、文字の背後に半透明の背景（ハロ）を敷いて可読性を確保する

仕様（design D6・D7・D11・D12・D13）自体は変えない。`tasks.md` §10 に検証タスク（目視確認）として追加する。

## Risks / Trade-offs

**[定義の違う2つの平均が同居する]** → D3 のとおり、凍結日を数えるかどうかで目標カード上に別々の「平均」が並ぶ。ラベルで意味を書き分け、目標カードに足すのは**完了予想日の1行だけ**にして、バーンアップ側の平均値そのものはカードに出さない。

**[単価が少ない標本で暴れる]** → 走行中の枝で葉を1つ終えただけで単価が確定し、残り想定が大きく振れる。これは「毎日動く」ことの裏返しであり、抑制しない。単価自体は画面に出さない（D6・D11 のとおり残り想定・単価は非表示、完了予想日という結果にだけ現れる）ので、実測由来か仮置きかを画面上で区別する必要も無くなった。

**[葉の粒度が揃っていない枝で単価が意味を失う]** → 単価は走行中の枝の中でだけ使うので、枝をまたいだ粒度の不揃いは影響しない。枝の中で粒度が崩れている場合は Gemini との合議で `estimated_seconds` を直接書き換える逃げ道が残っている。

**[ルール変更の理由が画面から読めなくなる]** → D1-c のとおり⑤沿革に代替が無い。閾値を下げた理由・凍結した理由・質問の答えが書き込み専用になる。`rule_change` / `goal_freeze_change` / `rule_answer` は削除しないので、後から読み手を足せる。理由必須の入力規則（`editable-rule-registry`）自体は変えない。

**[`task` への列追加が既存の一括更新経路に波及する]** → `progress_ratio` は葉のみに意味があり、容れ物では無視する。`subtree-done`（部分木の一括完了）で葉を done にしたとき `progress_ratio` を 1.0 と読み替える規則をサービス層に閉じ込め、呼び出し側で分岐させない。

**[デモモードで成果を見せられない]** → 日数が関わる機能なので、`demo-seed.ts` に固定 day_key のサンプルを足す。2ペースの完了予想日が離れて見えること（凍結明けの直近3日ペースが跳ねる様子）と、タスク達成マーカー（完了した根直下の枝2つ・走行中の枝の葉に同日2件完了する例を1つ含む）を再現する。足したら `demo.test.ts` の期待値も併せて更新する。既存の筋書き（達成 24/30・中盤の谷）を壊さないよう、サンプルは既存の谷日に寄せる。

**[新規 e2e を propose で書かない代わりに、参考モックとの差分がレビューされにくい]** → `ref/goal-burnup/burnup-mock.html` を実装の参考にする方針（D8）だが、これは拘束力のある仕様ではなく参考実装であり、乖離しても機械的には検出されない。実装後のレビューで `tasks.md` のチェック項目と突き合わせ、著しい乖離（達成マーカーの黒丸/白丸が逆転している等）が無いかを目視で確認する。
