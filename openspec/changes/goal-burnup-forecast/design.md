## Context

進行中の目標を開くと `renderReport()` が呼ばれ、完走後の振り返り用に作った5ブロック（①達成カレンダー ②時間の推移 ③写真の比較 ④日記ストリップ ⑤沿革）がそのまま出る。走っている最中に知りたい「いつ終わるのか」はどこにも無く、③④は素材が溜まっておらず、Check を続ける動機が生まれていない。完走後に開いても同じで、本人が「見たい要素が一つも入っていない」と判断している。したがってこの変更では**レポートを直すのではなく廃止**する。

一方で材料は既に揃っている:

| 材料 | 現在地 |
|---|---|
| 目標配下の親子タスク（容れ物と葉） | `task.parent_task_id` / `goal_id` / `tree_order`（`task-tree`） |
| 目標に紐づく作業時間の累積 | `goals.ts` の `accumulatedSecondsFor(db, row, dayKeys)` |
| 計測対象の指し方 | `goal_target_hours` + `goal_target_hours_member`、および目標に紐づく時間型ルール |
| 凍結期間 | `goalFreezeIntervals()` |
| 進行中／完走後の分岐 | `goalCard()` のボタン文言分岐（`goals.js:258`） |

足りないのは **残り想定時間（スコープ）** だけで、それは正確に測れる種類の数字ではない。ユーザーは Gemini と雑に合議して決めることを望んでおり、アプリはその数字を検算せずそのまま使う。

## Goals / Non-Goals

**Goals:**

- 目標を開いたとき、完了予想日が主役の1枚だけを出す（レポートは廃止し、ビューを1つに減らす）
- 完了予想日が **毎日動く**（累積は単調増加なので、必ず何かが動く）
- 完了予想日を手前へ動かす手が2系統ある（積む／削る）ことが画面で読める
- スコープが動いた理由が後から読める
- Gemini / Antigravity が HTTP 経由で見積もりを書き込める

**Non-Goals:**

- 見積もりの正確性。単価も仮置きも「それっぽい」で十分であり、精度を上げる仕組みは作らない
- 解錠ゲートへの合流。バーンアップは `unlock_evaluation` に一切現れない
- 複数の枝を同時に走らせること。走行中の枝は常に1つ
- ①③④⑤ に相当する画面の作り直し（廃止するだけで、移設先は用意しない）
- 夜のリザルト画面・通知など、見通しを開く以外の出口

## Decisions

### D1. レポートは capability ごと消す。ビューは見通し1つ

目標を開いたときの行き先を**見通し1つ**にする。レポート画面・`GET /api/goals/:id/report`・①〜⑤のブロック関数をすべて削除する。

```
today <  start_day  → 開けない（409）
today >= start_day  → 見通し（進行中は予測あり／完走後・終了後は予測なし）
```

目標カードのボタンは4つ（レポートプレビュー／タスク一覧／終える／削除）で、数を増やさない。文言だけ差し替える。

```
進行中  「見通し」 ／ タスク一覧 ／ 終える ／ (削除)
完走後  「続ける」 ／ タスク一覧 ／ 終える ／ (削除)
```

**代替案**: 進行中だけ差し替えて完走後はレポートを残す → 却下。完走後も開く動機が無いと本人が判断している。残すと①〜⑤の保守が続き、見通しと二重の読み手になる。
**代替案**: 「見通し」を第3のビューとして足す → 却下。カードの導線が5つになる。
**代替案**: 既存 E2E 3本が到達手段を失うのでレポートを残す → **却下**。E2E は仕様どおりかを確かめる手段であって、仕様を決める理由にならない。レポートしか検証していない2本は削除し、レポート経由で別の対象を見ていた2本はその区間を落とす。

### D1-b. フォークだけは落とせないので目標カードへ移す

レポートの中で唯一、表示ではなく**機構**なのが「続ける／終える」フォーク。答えるまで永続ルール（`end_day=null`）がゲートに残り続ける（`goal-lifecycle-fork`）ため、提示場所を失うと未回答の目標のルールを外す手段が消え、ゲートが永久に開かなくなる。

移設先は**目標カード**。完走カードの「レポートを開く」の位置に「続ける」が入り、既存の「終える」と2択になる。導線の数は変わらず、未回答の目標が一覧で目立つという副次効果もある。実装も既存を流用できる（「終える」＝`openEndDialog`、「続ける」＝`POST /api/goals/:id/continue`）。

### D1-c. 消える情報を正直に数える

レポートの廃止で**画面から読めなくなるもの**:

| 失うもの | 出どころ | 代替 |
|---|---|---|
| ①達成カレンダー・達成 N/M | `unlock_evaluation` | 無し（レコードは残る） |
| ③写真の比較 | `goal_journal_image` / `rule_answer` | 大きい沿革の終了・完走の行（Before→After） |
| ④日記ストリップ | `goal_journal` | 振り返りタブの目標コーナーで読み書き（`goal-journal`） |
| ⑤沿革（ルール操作の理由・凍結・答え合わせ） | `rule_change` / `rule_answer` / `goal_freeze_change` | **無し** |
| ①のマスから開く日別詳細 | 同上 | 振り返りタブ（`reflection-journal`） |

⑤の喪失が一番大きい。大きい沿革（`goal-history`）は「ルール操作・凍結イベント・日記を載せてはならない（MUST NOT）」と規定されており、引き取らない。**レコードは1件も消さない**ので、必要になった時点で別の画面へ出せる。

### D2. 計測対象は既存の指定から解決し、無いときは空状態にする

バーンアップの縦軸は累積作業時間なので、「何の時間を積むか」が要る。新しい指定枠は作らず、次の順で解決する。

1. `goal_target_hours` の対象（`kind` と members）— `seconds_per_day` は**使わない**（1日あたりの目標は別の意図の数字）
2. 目標に紐づく**時間型ルール**（`TOTAL_WORK` / `GROUP` / `TIMELINE`）の対象を束ねる
3. どちらも無ければ **空状態**（「何で測るかを決める」導線）

`goal-target-hours` の「目標時間の有無で処理を場合分けする例外（レポート構成の変更等）を設けてはならない（MUST NOT）」に抵触しないよう、**ブロックは常に出す**。目標時間を持たない目標でも見通しのビューは同じ構成で開き、中身が空状態になるだけとする。構成が変わるわけではない。

**代替案**: 目標時間を持つ目標にだけバーンアップを出す → 却下。上記 MUST NOT に正面から当たる。
**代替案**: 対象が無ければ全作業時間（`TOTAL_WORK`）へフォールバック → 却下。Udemy の目標に家計簿をいじった時間が混ざり、予想が静かに壊れる。

### D3. 凍結日はバーンアップでは 0h として数える。`goalPace()` は変えない

バーンアップは**暦どおり**に日を数え、凍結日も 0h の実績として累積線に含める。凍結で予想日が遠のき、復帰後に直近3日ペースが跳ねて大きく縮む — この谷と戻りが報酬になる。

一方、既存の `goalPace()`（目標時間のペース表示）は凍結日を分母から除いており、`goal-target-hours` にその要件がある（「凍結日を分母に数えてはならない・MUST NOT」）。**これは変更しない。**

同じ画面上に定義の違う2つの平均が並ぶことになるため、意味の違いをラベルで明示する:

| | 数える日 | 問い |
|---|---|---|
| 目標時間のペース（既存） | 凍結日を除く | 1日あたりの目標を守れているか |
| バーンアップのペース（新） | 凍結日を含む | 実際の暦でいつ終わるか |

**リスクとして残る。** 下の Risks に再掲する。

### D4. 想定時間は容れ物に持たせ、変更は別テーブルに追記する

```sql
ALTER TABLE task ADD COLUMN estimated_seconds INTEGER;      -- NULL = 未設定
ALTER TABLE task ADD COLUMN progress_ratio REAL;            -- 葉のみ・NULL = 未設定（done なら 1.0 扱い）

CREATE TABLE task_estimate_change (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  task_id INTEGER NOT NULL REFERENCES task(id),
  field TEXT NOT NULL,              -- 'estimate' | 'progress'
  from_value REAL,
  to_value REAL,
  reason TEXT NOT NULL,
  actor TEXT NOT NULL,              -- 'human' | 'agent'
  day_key TEXT NOT NULL,
  created_at INTEGER NOT NULL
);
```

`practice_threshold_change` / `rule_change` / `goal_freeze_change` と同じ「値は本体、履歴は別テーブル」の流儀に合わせる。理由を必須にするのは `goal-blueprint` の枝の打ち切りと同じ考え方で、段差の意味が後から読めなくなることを防ぐ。

**マイグレーションは新しいバージョンを足す。既存 migration の SQL を書き換えない**（過去に2回、書き換えたせいで実 DB へ反映されない事故が起きている）。

### D5. 走行中の枝は「未完了の葉を持つ、根直下の最初の枝」

`tree_order` 順に根直下の枝を見て、未決着の葉を持つ最初の枝を走行中とする。同時に2つは走らない。2つ同時に進めたい日があっても、そのためにロジックを複雑にしない（ユーザー決定）。

枝の**開始日**は、直前の枝が決着した日の翌日。直前の枝が無ければ目標の `start_day`。

### D6. 単価は走行中の枝でだけ実測から導き、仮置きを上書きする

```
枝の実測秒   = 枝の開始日〜今日の累積秒
枝の消化量   = その枝で完了した葉の重み合計（done = 1.0、未 done は progress_ratio）
単価         = 枝の実測秒 ÷ 枝の消化量
枝の残り想定 = 単価 × 残りの葉の重み合計
```

消化量が 0 のとき単価は出せないので、**Gemini の仮置き（`estimated_seconds`）をそのまま使う**。消化量が 0 より大きくなった時点で、実測由来の値が仮置きを上書きする。

これが提案の「要因3（単価の改善）」の実体で、**同じ時間だけ働いたのに予想が余計に縮む日**を作る。慣れて速くなったことが自動で報酬になる。

先の枝（まだ走っていない枝）は常に仮置きのまま。実測が無いので導きようがない。

**代替案**: 全枝で単価を導く → 却下。作業時間は枝ごとに分かれて記録されておらず、走行中の枝が1つだからこそ期間で切り出せる。

### D7. ペースは2本。全体平均と直近3日

```
全体平均 = 目標開始日〜今日の累積秒 ÷ 経過日数（凍結日を含む・今日を含む）
直近3日  = 直近3日の累積秒 ÷ 3（今日を含む）
```

完了予想日は、残り想定秒をペースで割った日数を**切り上げて**今日へ足した日。家計簿の月末予想が「日単価を先に整数へ切り捨ててから掛ける」と決めたのと同じ理由で、画面に出ている数字と算数が一致することを優先する。

ペースが 0（その期間に一切積んでいない）のとき、完了予想日を**出さない**。0 除算の表示を出してはならないという `kakeibo-forecast` の既存判断に合わせる。期限を越える予想は、越えたことが分かる形で**出す**（隠さない）。

### D8. 描画はインライン SVG

リポジトリには `chart.umd.min.js`（家計簿で使用）があるが、バーンアップに必要なのは折れ線ではなく **段差つきのスコープ線・2本の予測直線・交点マーカー・段差の理由ラベル**で、Chart.js では注釈プラグイン無しに置けない。参照実装（`ref/` へ入れる 2a）も SVG で描かれている。

インライン SVG で描き、Chart.js は家計簿のまま触らない。

### D9. 書き込みは既存の HTTP API 経由のみ。アプリは検算しない

```
GET  /api/goals/:id/burnup          見通し1枚ぶんの数字（サーバで計算済み）
PUT  /api/tasks/:id/estimate        { estimatedSeconds, reason }
PUT  /api/tasks/:id/progress        { ratio, reason }
```

`GET /api/goals/:id/burnup` は**計算済みの値**を返す。クライアントは描画に徹する（`kakeibo-forecast` の「予想の計算はすべてサーバが行い、クライアントは描画に徹する」と同じ）。

`PUT` は `reason` を必須とし、`task_estimate_change` へ1行追記する。`actor` はリクエスト元ではなく**明示的に渡させる**（誰が決めたかは画面に出る情報であり、推測させない）。

zod スキーマは `packages/contract/src/index.ts` に置く。外部エージェントが叩く口なので、型の drift をここで止める。

**アプリは受け取った数字を検算しない。** `ratio` が 0.8 でも 1.0 でも、それがどう決まったかには関知しない。柔軟性は「数字の決め方」の側に閉じ込め、算数は硬いままにする。

### D10. バーンアップは解錠ゲートに一切合流しない

`unlock_evaluation.per_condition_results` にバーンアップ由来のエントリが現れてはならない。完了予想日が遠のいてもパスワードは出る。`goal-target-hours` が同じ判断を既にしており、理由も同じ（当日評価と両立しない・下限とゴールの二段構えが消える）。

## Risks / Trade-offs

**[定義の違う2つの平均が同居する]** → D3 のとおり、凍結日を数えるかどうかで目標カード上に別々の「平均」が並ぶ。ラベルで意味を書き分け、目標カードに足すのは**完了予想日の1行だけ**にして、バーンアップ側の平均値そのものはカードに出さない。

**[単価が少ない標本で暴れる]** → 走行中の枝で葉を1つ終えただけで単価が確定し、残り想定が大きく振れる。これは「毎日動く」ことの裏返しであり、抑制しない。ただし単価が実測由来であることを画面で明示し、仮置きと区別する。

**[葉の粒度が揃っていない枝で単価が意味を失う]** → 単価は走行中の枝の中でだけ使うので、枝をまたいだ粒度の不揃いは影響しない。枝の中で粒度が崩れている場合は Gemini との合議で `estimated_seconds` を直接書き換える逃げ道が残っている。

**[ルール変更の理由が画面から読めなくなる]** → D1-c のとおり⑤沿革に代替が無い。閾値を下げた理由・凍結した理由・質問の答えが書き込み専用になる。`rule_change` / `goal_freeze_change` / `rule_answer` は削除しないので、後から読み手を足せる。理由必須の入力規則（`editable-rule-registry`）自体は変えない。

**[`task` への列追加が既存の一括更新経路に波及する]** → `progress_ratio` は葉のみに意味があり、容れ物では無視する。`subtree-done`（部分木の一括完了）で葉を done にしたとき `progress_ratio` を 1.0 と読み替える規則をサービス層に閉じ込め、呼び出し側で分岐させない。

**[デモモードで成果を見せられない]** → 日数が関わる機能なので、`demo-seed.ts` に固定 day_key のサンプル（交点が動く様子・段差が2つ以上）を足す。足したら `demo.test.ts` の期待値も併せて更新する。既存の筋書き（達成 24/30・中盤の谷）を壊さないよう、サンプルは既存の谷日に寄せる。
